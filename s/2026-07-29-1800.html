insane-search 차단 대응

공개 페이지 리더 도구 insane-search 소개 링크가 공유되고, 특정 쇼핑몰이 막혔는지 질문이 나옴. 플레이라이트로는 되는데 cffi 경로는 전부 막혔다는 확인이 있었고, 기능을 추가할수록 차단만 유발한다는 판단에 신규 기능 추가를 보류하는 쪽으로 기울었다. 도구 자체를 분석시키면 모델이 추천은 못하겠다는 반응을 낸다는 후일담도 나옴.

  • insane-search는 Claude Code용 공개 페이지 리더로 소개됨
  • cffi 기반 접근은 차단, 플레이라이트 경로는 아직 동작
  • 기능 추가 때마다 차단당할 것 같아 신규 기능 개발을 멈출지 고민 중
  • 기능을 안 넣으면 오히려 우회 난이도가 올라간다는 역설적 이유도 언급
  • https://github.com/fivetaku/insane-search/

요약봇 테스트와 아티팩트

요약 봇이 아직 테스트 중이며 현재 fable 모델로 돌고 있다는 설명이 나옴. 요약 품질이 떨어진다는 지적에는 메신저 대화가 비정형이라 빠르게 처리하면 노이즈가 많아진다는 답이 붙었다. 결과물을 아티팩트로 띄워봤지만 권한이 작성자 본인에게만 열려 깃허브 페이지로 바꾸기로 정리됨.

  • 요약 봇은 현재 fable 모델 기반으로 테스트 운영 중
  • 링크 요약 기능에 물려 있어 깃허브 레포 상세 분석은 안 됨 — 리드미를 읽는 별도 기능이 필요
  • 아티팩트는 자동 공유 시 본인만 열람 가능해 깃허브 페이지로 전환

워크스페이스 분할 관리

프로젝트 하나에 블록을 몰아넣는 구조와 상위 오케스트레이터 프로젝트를 두는 구조를 두고 질문이 오감. 오케스트레이터 방식은 작업이 늘수록 누락이 생기고 관리가 어려워져서, 세부 작업은 개별 워크스페이스에서 하고 상위 폴더는 파일 찾기·이력 확인 용도로만 쓴다는 답이 나왔다. 기능 단위 분할이 기준이며 정답은 아니라는 단서가 붙음.

  • 상위 오케스트레이터 단일 관리는 작업량이 늘면 누락과 관리 실패를 부름
  • 기능 단위로 워크스페이스를 쪼개고 세부 프로젝트·강의는 별도 운영
  • 답변자는 관리 중인 워크스페이스가 40~50개 규모
  • 같은 블록을 여러 곳에서 재사용하려는 욕심이 관리 난이도를 올리는 지점으로 지목됨

지식관리 도구 조언

  • 옵시디언은 그래프뷰로 자랑할 목적이 아니면 굳이 권하지 않음
  • 레퍼런스·아티클 축적은 클로드코드 워크스페이스 분할로 대체 가능
  • AI 생성물과 직접 작성물을 구분해 구성할 것
  • 생성만 하고 읽지 않는 문서는 캐싱 역할에 그친다는 판단

세션 인수인계 방법

  • 세션 종료 시 wrap 루틴을 만들어 상태를 정리
  • 프로젝트 내부에 KB 또는 SLLM 위키를 두고 지속 업데이트
  • 생성된 인수인계 문서는 누락·정확성을 직접 검수해야 함
  • 완료 항목 아카이브를 훅으로 빼고 핸드오프 문서 한 권으로 이어가는 시도도 공유됨
