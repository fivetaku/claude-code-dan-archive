OMP와 OMO 차이, 코딩 에이전트 선택과 설치 방법

OMP는 작업 공간을 갖춘 코딩 에이전트이고 OMO는 여러 모델과 에이전트를 조율하는 계층이다

2026-10-27논의 1회 정리

AI 코딩 도구를 찾다 보면 OMP와 OMO라는 약어가 함께 등장한다. 둘 다 터미널에서 코드를 다루지만, 하나는 작업을 수행하는 코딩 에이전트이고 다른 하나는 여러 에이전트와 모델을 조율하는 오케스트레이션 계층이다. 무엇이 다른지, OpenCode와 어떤 관계인지, 개인 개발자와 소규모 팀은 어디부터 써야 하는지가 이번 비교의 핵심이다.

OMP는 코딩 작업을 직접 수행하는 실행 환경이다

OMP는 현재 omp 명령으로 배포되는 Oh My Pi 계열의 코딩 에이전트다. 터미널에서 파일을 읽고 수정하며, 셸 명령과 테스트를 실행한다. 프로젝트 안에서 작업을 끝내는 데 필요한 도구를 한 화면에 묶은 제품에 가깝다.

공식 프로젝트는 OMP를 IDE 기능이 결합된 에이전트 하네스로 설명한다. LSP, 디버거, 브라우저 도구, 서브에이전트, Python 실행 환경을 제공하고, 다양한 모델 제공자를 연결할 수 있다. 모델을 바꾸더라도 같은 작업 인터페이스를 유지하는 구조다. (omp.sh)

설치 뒤에는 프로젝트 폴더에서 omp를 실행하고, 사용할 모델 제공자를 연결한다. 이후 자연어로 파일 수정이나 리팩터링을 지시하면 OMP가 저장소를 탐색하고 명령을 실행한다. 단일 프로젝트를 오래 붙잡고 작업하거나, LSP 진단과 테스트 실행을 한 흐름으로 묶고 싶다면 OMP가 먼저다.

다만 OMP가 여러 모델을 지원한다고 해서 작업마다 알아서 가장 적합한 모델을 고르는 것은 아니다. 기본 모델 역할과 제공자 설정은 사용자가 확인해야 한다. 실사용자 사이에서는 기능이 풍부하다는 평가와 함께, 모델별 도구 호출 형식이 맞지 않을 때 루프나 중단을 직접 점검해야 한다는 반응도 나온다.

OMO의 OpenCode용 에디션은 OpenCode 위에서 작동하는 조율 계층이다

OMO의 공식 명칭은 Oh My OpenAgent다. 이전 이름은 Oh My OpenCode였고, 현재 문서에는 OpenCode 플러그인, Codex용 에디션, 독립 실행형 OmO Native가 함께 설명돼 있다. 따라서 OMO를 ‘Claude 전용 버전’으로 이해하면 정확하지 않다. Claude는 연결할 수 있는 모델 계열 중 하나일 뿐이다. (omo.dev)

OMO가 하는 일은 사용자의 요청을 역할별 작업으로 나누는 것이다. 주 에이전트가 계획을 세운 뒤 탐색, 문서 확인, 설계, 구현, 검토 같은 작업을 별도 에이전트에 넘긴다. 각 역할에는 모델 우선순위와 대체 모델 목록을 둘 수 있다. 작업 성격에 따라 비싼 모델과 빠른 모델을 나누는 이유가 여기에 있다.

OpenCode는 여러 LLM 제공자와 로컬 모델을 연결하는 호스트다. 공식 문서는 API 키를 연결한 뒤 설정에서 제공자와 모델을 선택하는 방식을 안내한다. OMO는 그 위에서 에이전트 구성과 모델 매칭, 병렬 실행, 계획 검토 같은 흐름을 추가한다. (docs.opencode.ai)

이 차이를 한 문장으로 줄이면 이렇다. OMP는 ‘한 에이전트가 쓸 수 있는 작업 환경’이고, OMO는 ‘여러 에이전트가 어떤 순서와 모델로 움직일지 정하는 운영 계층’이다.

OMP와 OMO는 경쟁 제품보다 서로 다른 출발점이다

OMP는 설치 후 바로 프로젝트를 열고 작업하는 데 초점이 있다. 별도의 호스트를 먼저 준비하지 않아도 되고, 코딩·검색·셸·진단 도구가 한 실행 파일 안에서 작동한다. 모델과 도구를 직접 조정하면서 단순한 기능 추가나 버그 수정부터 시작하기 쉽다.

OMO의 기본 경로는 다르다. OpenCode를 설치한 뒤 bunx oh-my-openagent install을 실행해 플러그인을 등록하고, 연결된 모델과 에이전트 구성을 확인한다. 공식 설치 문서는 OpenCode용 opencode, Codex용 codex, 두 환경을 함께 쓰는 both를 구분한다. (github.com)

OMO는 요청 하나를 여러 단계로 확장할 때 강점을 보인다. 예를 들어 기존 저장소의 인증 구조를 바꾸는 작업이라면 탐색 에이전트가 관련 파일을 찾고, 설계 에이전트가 변경 범위를 제안하며, 구현 에이전트가 코드를 고친다. 마지막으로 테스트와 리뷰를 별도 흐름에 맡길 수 있다.

반대로 작은 작업에 OMO를 항상 켜면 호출 수와 설정 복잡도가 늘어난다. 실사용자들 사이에서도 자동 위임이 편리하다는 의견과, 단순한 수정에는 오케스트레이션이 과하다는 의견이 함께 나온다. 작업을 여러 역할로 나눌 이유가 있을 때 OMO의 이점이 커진다.

실제 사용은 호스트, 플러그인, 모델 순서로 시작한다

OMP를 시험할 때는 먼저 프로젝트 하나를 정하고, 읽기 중심 작업부터 요청하는 편이 안전하다. 예를 들어 “이 저장소의 테스트 실행 명령과 주요 진입점을 찾아 설명해 달라”고 지시한다. 이후 작은 버그 수정, 테스트 추가, 리팩터링 순서로 범위를 넓힌다. 수정 전후의 diff와 테스트 결과를 확인하면 에이전트의 도구 사용과 모델 품질을 함께 평가할 수 있다.

OpenCode용 OMO는 다음 순서가 명확하다. OpenCode를 설치하고, OMO 플러그인을 등록한 뒤, 사용할 제공자의 인증을 연결한다. 그다음 ~/.omo/omo.jsonc 또는 프로젝트의 .omo/omo.jsonc에서 모델과 에이전트 구성을 확인한다. 현재 문서는 하나의 통합 설정 파일이 여러 OMO 하네스에 적용되며, 프로젝트 설정이 사용자 설정보다 우선한다고 설명한다. (github.com)

처음부터 모든 에이전트를 켤 필요는 없다. 탐색과 구현을 분리하고, 마지막 검토만 별도로 호출하는 정도면 구조를 이해하기 쉽다. 모델 매칭은 자동화할 수 있지만, 각 역할에 어떤 모델이 연결됐는지와 실패 시 대체 경로가 있는지는 확인해야 한다.

여기서 중요한 산출물은 화면의 진행 애니메이션이 아니다. 어떤 파일을 읽었는지, 어떤 명령을 실행했는지, 어떤 테스트가 통과했는지, 최종 diff가 요구사항과 맞는지가 결과다. OMP든 OMO든 이 기록을 검토하지 않으면 여러 에이전트를 붙인 만큼 검증 부담도 커진다.

개인 개발자와 작은 팀의 선택 기준은 작업 규모다

혼자 만드는 웹 서비스에서 하루에 몇 개 파일을 고치고 테스트하는 정도라면 OMP가 더 짧은 경로를 제공한다. 단일 에이전트의 행동을 관찰하면서 모델과 도구를 조정하기 쉽고, 별도 오케스트레이션 설정도 필요하지 않다.

반면 요구사항 정리, 코드베이스 탐색, 구현, 리뷰를 반복하는 팀이라면 OMO가 유리할 수 있다. 역할별 모델을 지정하고 작업 단계를 나누면 같은 프로세스를 재사용할 수 있기 때문이다. OpenCode의 제공자 설정을 이용해 클라우드 모델과 로컬 모델을 섞는 선택지도 있다. (docs.opencode.ai)

다만 OMO를 설치한다고 결과가 자동으로 좋아지는 것은 아니다. 위임할 작업의 경계를 정하고, 에이전트가 수정할 수 있는 범위와 검증 명령을 프롬프트에 넣어야 한다. 모델 비용도 호출 수와 컨텍스트 크기에 따라 달라지므로, ‘여러 모델을 쓰면 항상 저렴하다’고 단정할 수 없다.

OMP와 OMO의 차이를 이해하는 가장 쉬운 방법은 같은 작은 작업을 각각에 맡겨 보는 것이다. OMP로 직접 탐색과 수정을 끝내 보고, 같은 작업을 OMO에서 탐색·구현·검토로 나눠 비교한다. 한 명의 에이전트로 충분한 문제라면 OMP가 남고, 역할 분리가 실제 시간을 줄이는 문제라면 OMO가 남는다.

자주 묻는 질문

Q

OMP와 OMO는 같은 도구인가요?

아닙니다. OMP는 터미널에서 코딩 작업을 수행하는 에이전트이고, OMO는 여러 에이전트와 모델을 조율하는 계층입니다. OMO는 OpenCode나 Codex 같은 호스트와 함께 사용할 수 있습니다.

Q

OMO는 Claude 전용 도구인가요?

아닙니다. OMO의 공식 명칭은 Oh My OpenAgent이며, Claude는 연결 가능한 모델 계열 중 하나입니다. OpenAI, Gemini, Kimi, 로컬 모델 등도 구성에 따라 사용할 수 있습니다.

Q

처음 시작할 때 OMP와 OMO 중 무엇을 써야 하나요?

작은 프로젝트에서 파일 수정과 테스트를 직접 경험하려면 OMP가 간단합니다. 탐색·설계·구현·검토를 여러 역할로 나눠야 한다면 OpenCode와 OMO 조합을 검토할 만합니다.
