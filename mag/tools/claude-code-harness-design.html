Claude Code 하네스, 크게 짜기 전에 나눠야 할 네 가지

스킬·서브에이전트·훅·worktree의 역할을 나눠 작은 팀이 만드는 최소 구조와 검증 순서를 짚었다

2026-09-04논의 1회 정리

Claude Code가 스킬과 서브에이전트, 훅, worktree를 모두 품으면서 '하네스를 얼마나 크게 짜야 하나'가 새 과제가 됐다. 코딩 에이전트 위에 또 하나의 거대한 에이전트 시스템을 올려야 할까. 이 글은 네 구성 요소의 역할을 나누고, 작은 팀이 실제로 만들 최소 구조를 짚는다.

거대한 하네스보다 얇은 운영층이 먼저다

Anthropic은 Claude Code를 코드베이스를 이해하고 명령을 실행하는 에이전트형 코딩 도구로 정의한다. 터미널과 IDE에서 파일을 읽고 고치며 Git 작업도 처리한다. 출발점부터 실행 주체가 있으므로, 하네스의 첫 임무는 새 두뇌를 만드는 일이 아니다.

클코단 논의에서는 프롬프트와 Markdown, 훅을 묶어 작업 환경을 다듬자는 의견이 많았다. 이 관점은 공식 플러그인 구조와도 맞는다. Anthropic 저장소의 플러그인 안내는 commands, agents, skills, hooks, MCP를 독립 구성 요소로 둔다. 그렇다고 하네스가 클수록 성능이 좋아진다는 공식 보장은 없다. 써본 사람들 사이에서는 긴 프로젝트 지침과 많은 스킬 설명이 문맥을 차지한다는 불만도 나온다. 규칙이 늘수록 충돌 원인을 찾기 어렵다는 반응도 있다.

크기보다 책임 경계가 먼저인 이유다.

CLAUDE.md와 SKILL.md, 서브에이전트는 역할이 다르다

프로젝트 공통 규칙은 `CLAUDE.md`에 둔다. 빌드 명령, 폴더 규약, 금지 작업처럼 모든 요청에 적용할 내용이 맞다. 특정 작업에서만 필요한 절차까지 밀어 넣으면 매 세션의 기본 문맥이 무거워진다.

반복 업무는 `.claude/skills/<이름>/SKILL.md`로 뺀다. Anthropic의 Skill Development 문서는 스킬을 전문 지식과 작업 흐름을 담는 모듈로 설명한다. 필수 파일은 YAML 프론트매터와 Markdown 본문을 가진 `SKILL.md`다. 재사용 코드는 `scripts/`, 상세 문서는 `references/`, 결과물 재료는 `assets/`에 둔다.

서브에이전트 정의도 Markdown과 YAML 프론트매터를 쓴다. 닮은 형식 때문에 둘을 같은 것으로 보기 쉽다. 그러나 스킬은 메인 에이전트가 불러 쓰는 절차다. 서브에이전트는 별도 문맥에서 자율 작업을 맡는 실행자다. 공식 Agent Development 문서도 에이전트를 복잡한 다단계 작업용 subprocess로 구분한다.

파일을 하나 만들 때는 `.claude/agents/code-reviewer.md`처럼 둔다. 프론트매터에는 이름, 호출 조건, 모델, 허용 도구를 적는다. 본문에는 책임, 작업 순서, 품질 기준, 반환 형식을 쓴다. 읽기 전용 검토라면 `Read`, `Grep`, `Glob`만 허용해 범위를 줄일 수 있다.

훅은 지침을 실행 가능한 경계로 바꾼다

"테스트를 실행하라"는 문장은 모델이 해석한다. 훅은 사건이 발생할 때 코드를 실행한다. Anthropic의 Hook Development 문서는 훅을 검증, 정책 집행, 문맥 주입, 외부 도구 연동에 쓰는 이벤트 자동화로 규정한다.

`PreToolUse`는 도구 실행 전에 입력을 허용하거나 막고 바꿀 수 있다. `PostToolUse`는 실행 결과를 검사한다. `Stop`과 `SubagentStop`은 에이전트가 끝내려 할 때 완료 조건을 확인한다. `SessionStart`는 세션 시작 시 필요한 환경과 문맥을 불러온다.

만드는 순서도 단순하다. 먼저 막아야 할 사건 하나를 고른다. 다음으로 `.claude/settings.json`에 matcher와 command를 연결한다. 스크립트는 표준 입력의 JSON을 읽고 종료 코드나 구조화된 JSON을 돌려준다. 입력은 도구 이름과 인수다. 산출물은 허용·차단 결정이나 Claude가 읽을 피드백이다.

공식 저장소의 Bash validator 예제는 `PreToolUse`로 Bash 명령을 검사한다. 규칙에 걸리면 표준 오류로 이유를 보내고 종료 코드 2로 실행을 차단한다. 작은 팀이라면 비밀 파일 쓰기, 배포 명령, 테스트 누락처럼 손실이 큰 경계부터 자동화하면 된다.

다만 훅을 만능 안전장치로 보면 위험하다. 최신 변경 기록에는 권한 규칙, 플러그인 훅, 서브에이전트 실행과 관련한 수정이 계속 등장한다. 써본 사람들 사이에서도 서브에이전트 안에서 훅의 문맥이나 실행 범위가 예상과 달랐다는 경험이 있다. 중요한 차단 규칙은 메인 세션과 서브에이전트에서 각각 재현해야 한다.

최소 하네스는 한 업무를 끝까지 통과시키며 만든다

처음부터 범용 프레임워크를 설계하지 않는다. 예를 들어 PR 검토 하나를 고른다. `CLAUDE.md`에는 저장소 공통 명령만 적는다. `skills/review/SKILL.md`에는 검토 순서와 체크리스트를 둔다. `agents/code-reviewer.md`에는 읽기 전용 도구와 보고 형식을 제한한다.

그다음 `PostToolUse`로 변경 뒤 진단을 실행하거나, `Stop`으로 필수 검증 누락을 확인한다. 병렬 수정이 필요할 때만 에이전트 정의에 worktree 격리를 붙인다. PR 목표와 변경 파일을 입력받아 심각도순 발견 사항과 실제 검증 결과를 내놓는 구조다.

Anthropic의 공식 플러그인 저장소도 같은 조합을 보여준다. code-review 플러그인은 여러 전문 에이전트를 묶는다. security-guidance는 `PostToolUse`를 쓴다. feature-dev는 명령과 에이전트를 결합한다. 구성 요소를 모두 쓰는 게 아니라, 실패 가능성에 맞춰 고른 사례들이다.

worktree는 병렬화보다 실패 반경을 줄일 때 값이 있다

worktree 격리는 여러 에이전트가 같은 체크아웃을 덮어쓰지 않게 한다. 하지만 모든 서브에이전트에 붙이면 브랜치와 미반영 변경을 관리할 일이 늘어난다. 조사나 문서 읽기처럼 쓰기가 없는 작업에는 별도 worktree가 필요하지 않다.

공개 재현 사례에서는 worktree 경로 판정과 세션 정리, 플랫폼별 경로 처리에서 마찰이 보고됐다. 제품 하자로 일반화할 근거는 부족하다. 다만 격리를 켰다는 사실만으로 안전을 가정하면 안 된다. 생성, 변경 회수, 충돌 처리, 삭제까지 실제 운영 경로를 시험해야 한다.

하네스의 크기는 파일 수가 아니라 실패 하나를 통제하는 데 필요한 경계로 정해야 한다. 공통 규칙은 `CLAUDE.md`, 반복 절차는 스킬, 독립 문맥은 서브에이전트, 강제 조건은 훅이 맡는다. 이 네 책임이 겹치기 시작하는 순간, 더 큰 하네스가 아니라 구조를 덜어낼 때다.

자주 묻는 질문

Q

Claude Code 하네스는 무엇으로 구성하나요?

보통 CLAUDE.md, 스킬, 서브에이전트, 훅, MCP, worktree를 조합한다. 모든 요소를 넣기보다 반복 절차와 강제 조건부터 분리하는 편이 낫다.

Q

Claude Code 스킬과 서브에이전트의 차이는 무엇인가요?

스킬은 현재 에이전트가 불러 쓰는 지식과 절차다. 서브에이전트는 별도 문맥과 도구 범위에서 독립 작업을 수행한다.

Q

Claude Code 훅은 언제 써야 하나요?

실행 전 차단, 실행 후 검사, 종료 조건처럼 반드시 지켜야 할 경계에 쓴다. 단순 조언이나 업무 지식은 CLAUDE.md나 SKILL.md가 더 알맞다.
