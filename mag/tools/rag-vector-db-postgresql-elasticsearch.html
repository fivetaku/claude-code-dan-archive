RAG에 벡터DB가 꼭 필요할까, PostgreSQL·Elasticsearch 선택법

벡터DB와 RAG를 혼동하지 않고, PostgreSQL·Elasticsearch로 어디까지 구현할지 판단하는 실전 기준을 정리했다.

2026-10-24논의 1회 정리

RAG를 처음 만들 때 가장 자주 나오는 질문은 “전용 벡터DB를 따로 써야 하나?”다. 벡터DB, 시맨틱 서치, Elasticsearch, PostgreSQL이 모두 검색에 등장하면서 제품 선택보다 개념 구분이 먼저 필요해졌다. 이 글은 작은 서비스와 기존 데이터베이스를 가진 팀이 어떤 검색 구조를 선택해야 하는지에 답한다.

벡터DB와 RAG는 같은 제품이 아니다

벡터DB는 임베딩 벡터를 저장하고 질문 벡터와 가까운 데이터를 찾는 저장·검색 계열이다. RAG는 검색 결과를 LLM의 입력 문맥에 넣어 답변을 생성하는 애플리케이션 패턴이다.

문서를 RAG에 넣는 과정은 대체로 네 단계다. 원문을 적당한 청크로 나누고 각 청크를 임베딩 모델에 보낸다. 모델이 반환한 숫자 배열과 원문, 파일명, 권한, 날짜 같은 메타데이터를 저장한다. 사용자가 질문하면 질문도 벡터로 바꾼 뒤 가까운 청크를 찾는다. 그 결과를 LLM에 전달한다.

OpenAI 문서에 따르면 text-embedding-3-small의 기본 벡터 길이는 1536차원이고, text-embedding-3-large는 3072차원이다. dimensions 매개변수로 크기를 줄일 수도 있지만 저장 공간과 검색 비용이 줄어드는 대신 정확도가 달라질 수 있다. (developers.openai.com)

RAG를 만든다고 자동으로 전용 벡터DB가 필요한 것은 아니다. 필요한 기능은 임베딩 저장, 유사도 계산, 메타데이터 필터, 원문 조회, 그리고 검색 결과를 LLM에 넘기는 연결부다.

의미 검색은 임베딩·거리·인덱스가 나눠 맡는다

“비슷한 문장”을 찾는 기준은 문자열 일치가 아니다. 임베딩 모델이 문장을 다차원 좌표로 바꾸고 검색 시스템이 두 좌표 사이의 거리를 계산한다. 코사인 거리, 내적, 유클리드 거리는 그 비교 방식을 뜻한다.

HNSW는 의미를 만드는 모델이 아니다. 이미 만들어진 벡터를 빠르게 찾기 위한 근사 최근접 이웃 인덱스다. pgvector 문서는 HNSW가 IVFFlat보다 속도와 재현율의 균형에서 유리할 수 있지만 인덱스 생성 시간이 길고 메모리를 더 사용할 수 있다고 설명한다. IVFFlat은 벡터를 여러 목록으로 나눈 뒤 가까운 목록 일부만 검색한다. (github.com)

청크 크기도 검색 품질을 좌우한다. 너무 작으면 질문에 필요한 맥락이 쪼개지고 너무 크면 관련 없는 내용이 함께 검색된다. 방 논의에서도 토큰 단위로 청크 크기를 조정하는 것이 인덱싱 효율의 출발점이라는 의견이 나왔다. 다만 모든 문서에 같은 크기를 적용하기보다 제목, 문단, 표, 코드 블록의 경계를 함께 고려해야 한다.

실제 사용 경험을 공유한 사람들 사이에서는 벡터 검색만으로는 고유명사, 제품 코드, 법 조항 번호를 놓칠 수 있다는 불만이 반복된다. 반대로 키워드 검색만 쓰면 표현이 달라진 질문을 놓친다는 반응도 있다. 그래서 최근 검색 시스템은 두 방식을 함께 쓰는 하이브리드 구조로 기울고 있다.

PostgreSQL은 작은 RAG의 시작점이 될 수 있다

이미 PostgreSQL을 운영 중이라면 pgvector를 먼저 검토할 이유가 있다. pgvector는 별도 데이터베이스가 아니라 PostgreSQL 확장 기능이며 벡터와 기존 행 데이터를 같은 트랜잭션과 SQL 환경에서 다룬다. 원문, 사용자 ID, 문서 상태, 접근 권한을 한 테이블이나 연결된 테이블에서 관리할 수 있다.

구현 순서는 비교적 단순하다. documents 테이블에 content, embedding, metadata, source_id 같은 컬럼을 만든다. 문서를 청크로 나눈 뒤 임베딩을 생성해 저장한다. 질문이 들어오면 같은 임베딩 모델로 질문 벡터를 만들고 코사인 연산자와 HNSW 인덱스로 상위 결과를 조회한다. 반환된 content와 출처 정보를 프롬프트에 넣어 LLM을 호출하면 최소 RAG가 완성된다.

이 구조는 문서 수가 아직 크지 않고 서비스 데이터와 검색 데이터의 일관성이 중요한 팀에 맞는다. 주문, 고객, 문서 권한을 따로 동기화하지 않아도 되기 때문이다. 작은 제품을 만드는 개인 개발자에게는 인프라 하나를 더 운영하지 않아도 된다는 점이 특히 크다.

대신 벡터 검색이 전체 시스템의 가장 큰 부하가 되면 병목을 측정해야 한다. HNSW 메모리 사용량, 필터가 걸린 검색의 재현율, 인덱스 생성 시간, 임베딩 재생성 비용을 함께 봐야 한다. 필터 조건이 많거나 데이터 규모가 급격히 커지면 전용 검색 시스템이 더 적합할 수 있다.

Elasticsearch는 키워드와 의미를 한 흐름에 묶는다

Elasticsearch의 강점은 역색인 기반 전문 검색과 벡터 검색을 한 엔진에서 조합하는 데 있다. 공식 문서는 dense_vector와 sparse_vector 필드로 벡터를 저장하고 전문 검색·필터·집계와 결합할 수 있다고 설명한다. (elastic.co)

예를 들어 사용자가 “작년 휴가 규정”을 검색하면 키워드 검색은 “휴가”와 “규정”이 정확히 들어간 문서를 찾는다. 벡터 검색은 “연차 사용 기준”처럼 표현이 다른 문서를 끌어올린다. Elasticsearch의 하이브리드 검색은 두 결과를 합쳐 하나의 순위 목록으로 만들며 공식 문서는 Reciprocal Rank Fusion, 즉 RRF 방식을 권장한다. (elastic.co)

Elasticsearch는 기존 로그, 상품, 문서 검색을 이미 운영하는 팀에 자연스럽다. 검색어 분석, 필터, 집계, 권한 조건을 한 시스템에서 처리할 수 있기 때문이다. 반면 단순한 내부 문서 Q&A를 만들기 위해 새 클러스터를 추가한다면 운영 복잡도가 PostgreSQL보다 커질 수 있다.

방 논의에서 나온 “Elasticsearch는 키워드 검색이 중심이고 벡터 검색도 지원한다”는 구분은 실무적으로 유효하다. Elasticsearch가 벡터DB처럼 동작할 수 있다는 사실과 모든 RAG에 Elasticsearch가 최선이라는 주장은 서로 다르다.

전용 벡터DB로 옮길 시점은 검색 요구에서 결정된다

Pinecone, Qdrant, Milvus 같은 전용 시스템은 벡터 검색과 메타데이터 필터를 중심으로 설계됐다. Qdrant는 벡터와 함께 저장한 payload에 조건을 걸고 dense vector·sparse vector·BM25 결과를 조합하는 기능을 제공한다. (qdrant.tech) Milvus도 HNSW 같은 근사 최근접 이웃 인덱스와 스칼라 필터를 지원한다. (milvus.io)

전용 제품을 고려할 신호는 분명하다. 벡터 검색량이 기존 트랜잭션 DB와 분리돼야 하거나 여러 임베딩을 한 객체에 저장해야 하거나 검색 지연시간과 확장 정책을 별도로 최적화해야 할 때다. 대규모 데이터에서 필터와 재랭킹을 자주 조합하는 서비스도 전용 시스템의 장점을 활용할 수 있다.

그렇다고 제품 이름부터 고르면 안 된다. 먼저 검색 품질을 평가할 질문 목록을 만든다. 정답 문서가 상위 몇 개 안에 들어오는지, 권한 밖 문서가 노출되지 않는지, 고유명사와 숫자를 놓치지 않는지 측정한다. 그 결과가 나온 뒤 저장소를 바꿔야 비용과 품질을 함께 비교할 수 있다.

RAG의 핵심은 “벡터DB를 썼는가”가 아니다. 질문에 맞는 청크를 안정적으로 찾고 그 근거를 LLM에 정확히 전달하는가다. 기존 PostgreSQL이나 Elasticsearch가 이 요구를 충족한다면 그것이 가장 현실적인 출발점이고 검색 규모와 복잡도가 경계를 넘을 때 전용 벡터DB를 선택하면 된다.

자주 묻는 질문

Q

RAG를 만들려면 벡터DB가 반드시 필요한가?

반드시 필요하지 않다. PostgreSQL의 pgvector나 Elasticsearch의 벡터 기능으로도 임베딩 저장과 유사도 검색을 구현할 수 있다.

Q

pgvector와 Elasticsearch 중 무엇을 선택해야 하나?

기존 서비스 데이터와 권한 정보를 SQL로 함께 관리한다면 pgvector가 편하다. 전문 검색, 필터, 집계를 이미 Elasticsearch에서 운영한다면 Elasticsearch가 자연스럽다.

Q

RAG 검색 품질을 높이려면 무엇부터 바꿔야 하나?

먼저 청크 경계와 임베딩 모델을 점검하고, 키워드 검색과 벡터 검색을 함께 평가한다. 이후 HNSW 설정이나 재랭킹보다 정답 문서가 검색되는지부터 측정해야 한다.
