Codex 사용 한도가 빨리 줄어들 때, 작업 범위와 모델을 어떻게 바꿀까

리셋 직후에도 한도가 빠르게 줄어드는 이유를 살피고, 작업 단위·컨텍스트·모델 선택을 조정하는 방법을 짚는다.

2026-10-26논의 1회 정리

리셋된 지 얼마 되지 않았는데 Codex 사용 한도가 다시 줄어든다. 클코단에서도 비슷한 경험이 공유됐고, 작업을 작게 나누자는 제안이 나왔다. 한도를 아끼면서 코드 작업을 끝내려면 무엇을 바꿔야 할까?

사용량은 요청 횟수보다 작업의 무게에 좌우된다

OpenAI 도움말에 따르면 Codex 사용량은 모델, 작업 복잡도, 컨텍스트, 추론 수준, 속도 설정, 도구 사용에 영향을 받는다. 짧은 질문 한 번과 저장소를 훑고 테스트까지 실행하는 요청 한 번은 같은 무게가 아니다. 긴 작업은 짧은 요청보다 훨씬 많은 한도를 사용할 수 있다. (help.openai.com)

먼저 어떤 한도가 줄었는지 구별해야 한다. 해당 한도가 있는 요금제에서는 같은 사용량이 5시간 한도와 주간 한도에 함께 반영되지만, 두 기간의 종료 시점은 다를 수 있다. Codex CLI에서는 /status, 계정 화면에서는 사용량 설정을 확인할 수 있다. (help.openai.com)

리셋도 추가 한도를 무한히 쌓아 주지는 않는다. OpenAI는 일회성 리셋이 대상 한도를 복원하지만 요금제의 기본 한도를 영구적으로 늘리지는 않는다고 설명한다. 구매형 즉시 리셋은 새 주간 기간의 시작 시점에도 영향을 준다. 사용 가능 여부와 다음 갱신 시각은 계정 화면에서 확인해야 한다. (help.openai.com)

빠르게 닳는다는 체감은 다른 사용자들에게도 있다. 다만 개별 경험만으로 한도가 일률적으로 축소됐다거나 특정 모델에 문제가 있다고 판단할 수는 없다. 우선 실제로 소진된 기간과 해당 작업의 설정을 따로 봐야 한다. (help.openai.com)

파일을 지정할 때는 성공 조건도 함께 적는다

클코단에서는 큰 요청을 여러 작업으로 나누고 파일과 함수 범위를 알려 주자는 의견이 나왔다. 실패했을 때 되돌아갈 범위가 작아진다는 이유다. 그렇다고 요청을 한 줄씩 쪼개면 매번 맥락을 다시 설명하고 수정하는 비용이 생긴다.

OpenAI의 Codex 프롬프팅 가이드 역시 같은 파일을 반복해서 조금씩 고치기보다 필요한 문맥을 읽고 관련 변경을 묶으라고 권한다. 작은 작업의 기준은 문장 길이가 아니라 독립적으로 확인할 수 있는 결과다. 예컨대 ‘로그인 기능 개선’보다 ‘인증 실패 응답을 고치고 해당 테스트를 통과시켜 달라’가 범위를 판단하기 쉽다. (developers.openai.com)

요청에는 수정 대상, 건드리지 않을 곳, 완료 조건을 함께 넣을 수 있다. ‘src/auth/handler.ts의 오류 처리 함수를 살펴봐 줘. 공개 응답 형식은 유지하고, 관련 테스트 실패 원인을 확인한 뒤 필요한 부분만 수정해 줘’처럼 쓰는 식이다. 경로를 정확히 모르면 처음부터 파일명을 지어내기보다 관련 파일을 먼저 찾고 범위를 보고하게 하는 편이 낫다.

범위를 좁힌다고 영향 확인까지 생략하라는 뜻은 아니다. 공유 타입이나 호출부가 얽혀 있다면 인접 파일과 테스트도 살펴야 한다. OpenAI 가이드는 국소 변경을 하더라도 연결된 동작이 일관되게 유지되는지 확인하도록 권한다. (developers.openai.com)

실행 전에 계획을 보는 일이 절약이 되는 경우

클코단에서는 실행 전에 계획을 검토하자는 제안도 있었다. 여러 파일을 바꾸는 작업이라면 검색 방향이 어긋난 사실을 코드를 모두 고친 뒤에야 알아차리는 일을 줄일 수 있다. 위험한 변경에 앞서 Plan mode로 구현 경로를 제안받는 방식은 OpenAI의 Codex 작업 안내에도 나온다. (developers.openai.com)

계획을 요청할 때는 예상 수정 파일, 확인할 테스트, 변경하지 않을 범위를 적게 하면 검토하기 좋다. 계획에 저장소 전체 재구축처럼 목표보다 큰 단계가 들어 있다면 실행 전에 줄일 수 있다. 반대로 오타 한 곳을 고치는 일까지 매번 긴 계획으로 시작할 필요는 없다.

계획 자체도 작업이므로 무료 절약 장치는 아니다. 한 번의 계획 검토가 값어치를 하는 경우는 잘못된 탐색이나 대규모 재작업을 피할 가능성이 클 때다. 개인 개발자나 작은 팀이라면 변경 영향이 큰 인증·결제 경로와 단순 표시 수정을 같은 방식으로 다루지 않아도 된다.

긴 세션을 끊는다고 한도가 복원되지는 않는다

대화가 길어지면 이전 명령 출력과 실패한 시도가 현재 문제의 문맥에 섞인다. 클코단에서는 긴 세션을 새로 시작하자는 의견이 나왔다. 다만 새 대화는 리셋 버튼이 아니다. 기존 작업의 결정까지 잃으면 조사부터 반복할 수 있다.

OpenAI의 Codex 안내에는 현재 상태를 확인하는 /status와 긴 대화의 문맥을 압축하는 /compact가 소개돼 있다. 같은 목표를 이어 간다면 압축이, 별개 목표로 넘어간다면 새 작업이 더 어울린다. 작업을 옮길 때는 수정 파일, 확인된 원인, 실패한 시도, 남은 테스트를 짧게 남겨야 앞선 비용을 다시 치르지 않는다. (developers.openai.com)

팀에서 같은 설명을 자주 반복한다면 저장소 지침을 정리하는 방법도 있다. OpenAI의 작업 흐름 예시는 AGENTS.md에 목표, 코딩 관례, 테스트 기준, 작업 경계를 기록한다. 일회성 오류 로그까지 쌓기보다 다음 작업에도 필요한 정보만 남기는 용도다. (developers.openai.com)

가벼운 모델로 바꾸기 전에 확인할 것

단순 작업에는 가벼운 모델이나 낮은 추론 수준을 쓰고 어려운 디버깅에 Codex를 집중하자는 의견도 있었다. OpenAI는 모델과 추론 수준을 작업 전에 선택하고 결과를 본 뒤 필요할 때 추론 수준을 올리라고 안내한다. 다만 선택지는 요금제와 작업 환경에 따라 다르다. (help.openai.com)

모델을 바꿔도 이미 닳은 공용 한도가 돌아오지는 않는다. OpenAI는 공용 사용량 풀에서 모델을 전환해도 잔여 한도가 복원되지 않는다고 명시한다. 낮은 설정으로 여러 번 실패해 결국 같은 작업을 반복한다면 절약 효과도 기대하기 어렵다. (help.openai.com)

다른 도구에 주력 작업을 맡기고 Codex를 코드 문제에 쓰자는 선택은 각자의 작업 흐름에 달려 있다. 하지만 한도가 부족한 순간 먼저 판단할 대상은 도구의 이름보다 이번 요청이 어디까지 탐색하고 무엇을 끝내야 하는지다.

자주 묻는 질문

Q

Codex는 왜 리셋 직후에도 한도가 빨리 줄어드나요?

사용량은 요청 횟수만이 아니라 모델, 작업 길이, 컨텍스트, 추론 수준, 도구 사용에 따라 달라집니다. /status나 계정의 사용량 화면에서 5시간·주간 한도 중 무엇이 줄었는지 먼저 확인하세요.

Q

Codex에서 새 세션을 시작하면 사용 한도가 절약되나요?

새 세션을 시작해도 소진된 한도가 복원되지는 않습니다. 긴 대화의 불필요한 문맥을 덜어낼 수 있지만, 이전 결정과 실패 기록을 잃으면 같은 조사를 반복할 수 있습니다.

Q

Codex 작업을 얼마나 작게 나누는 게 좋나요?

한 번에 검증할 수 있는 결과를 기준으로 나누는 편이 좋습니다. 수정 대상과 완료 조건을 적되, 관련 호출부와 테스트를 확인할 여지는 남겨 두세요.
