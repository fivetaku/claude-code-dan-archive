낮은 품질의 OpenAPI 데이터, AI 에이전트만으로 정제할 수 있나

OpenAPI 검증부터 의미 보정과 사람의 최종 확인까지, 확률형 에이전트를 데이터 파이프라인에 넣는 현실적인 방법

2026-10-27논의 1회 정리

낮은 품질의 OpenAPI 데이터를 AI 에이전트에게 맡기면 전처리와 후보정까지 끝낼 수 있을까. 현장 경험은 단순한 자동화만으로는 부족하다고 말한다. 이 글은 어디까지 자동화하고 어느 지점에서 사람이 개입해야 하는지 답한다.

OpenAPI 명세는 데이터 품질 보증서가 아니다

OpenAPI는 API의 경로, 메서드, 파라미터, 응답 구조를 설명하는 표준이다. 공식 명세는 스키마가 많은 오류를 잡지만 모든 위반을 검출하지는 못한다고 명시한다. 형식 검증을 통과해도 필드 설명이 빈약하거나 실제 응답이 문서와 다를 수 있다.

유럽연합 데이터 품질 가이드도 같은 지점을 짚는다. API에는 구조뿐 아니라 데이터의 의미와 접근 방식도 설명돼야 한다. customer_id라는 이름만으로는 내부 고객번호인지 외부 식별자인지 알 수 없다. status가 결제 상태인지 배송 상태인지도 스키마만으로 확정하기 어렵다.

방 논의에서 낮은 품질의 OpenAPI를 다룰 때 사람이 직접 확인해야 한다는 의견이 많았던 이유다. 에이전트는 누락된 설명을 문맥으로 추정할 수 있지만 업무 현장에서 쓰이는 의미까지 자동으로 확정하지는 못한다.

자동화는 검증·변환·판단을 분리해야 한다

실전 파이프라인에서는 먼저 원본을 보존해야 한다. openapi.yaml 또는 openapi.json을 저장하고 API 응답도 날짜와 요청 조건을 포함해 별도 원본 디렉터리에 둔다. 이후 스키마 검증기와 요청·응답 검증기를 통과시킨 결과만 정제 단계로 넘긴다.

OpenAPI-core 같은 도구는 명세에 정의된 스키마를 기준으로 요청과 응답을 검사한다. 날짜, UUID, 숫자 형식처럼 기계적으로 확인할 수 있는 항목은 규칙 엔진이 담당해야 한다. 누락값, 중복 키, 타입 불일치, 허용 범위 밖의 값도 같은 단계에서 처리한다.

그다음 LLM은 의미 후보를 제안한다. 예를 들어 amt를 금액으로 볼지 수량으로 볼지, 두 날짜 필드의 선후관계가 무엇인지 추정하게 한다. 모델의 산출물은 원본에 곧바로 덮어쓰지 않고 mapping_candidates.json 같은 검토용 파일에 기록한다.

자동화의 산출물은 정답 데이터가 아니라 검토 가능한 후보여야 한다.

사람이 봐야 하는 데이터는 따로 표시해야 한다

현실 세계와 가까운 데이터일수록 의미 판단에 드는 비용이 커진다. 주소, 의료 기록, 재고 상태, 계약 단계처럼 같은 단어가 조직마다 다르게 쓰이는 영역이 그렇다. 모델이 가장 그럴듯한 의미를 고르더라도 업무 규칙과 일치한다는 보장은 없다.

NIST의 생성형 AI 지침은 자동 처리에서 놓칠 수 있는 맥락과 한계를 확인하도록 사람의 검토 절차를 두라고 권고한다.

에이전트는 불확실한 행을 숨기지 말고 격리해야 한다. 근거가 부족한 매핑, 서로 충돌하는 필드 설명, 값 분포가 갑자기 바뀐 항목에 needs_review 표시를 붙인다. 사람은 전체 데이터를 다시 읽는 대신 이 목록과 대표 샘플을 확인한다.

이 구조라면 사람의 역할이 병목이 아니라 품질 게이트가 된다. 검토 결과는 승인·수정·반려로 남기고 다음 실행에서 같은 규칙을 재사용한다.

LLM의 확률성은 결정론적 단계로 감싸야 한다

LLM은 같은 입력에서도 결과가 달라질 수 있다. 코드 생성 실험에서는 temperature를 0으로 낮춰도 결과의 비결정성이 사라지지 않았다. 호스팅 환경에서는 모델 버전과 실행 환경에 따라 결과가 달라질 수 있다.

LLM에게 데이터 정제 전체를 맡기면 재실행 때 다른 보정이 나올 수 있다. 같은 원본에서 매번 다른 표준화 결과가 나오면 감사 추적과 오류 재현이 어려워진다. 결정이 필요한 부분은 코드와 규칙으로 고정하고 의미 추정이 필요한 부분만 모델에 맡겨야 한다.

권장 순서는 간단하다. 원본을 해시로 고정하고 모델 이름과 프롬프트 버전을 기록한다. 모델 출력은 구조화된 JSON으로 제한한 뒤 JSON Schema로 다시 검사한다. 승인된 변환만 버전 관리되는 코드나 규칙 파일로 승격한다.

정제 후에는 샘플 비교, 행 수 변화, 주요 필드 분포, 금액 합계 같은 회귀 검사를 실행한다. 이전 결과와 달라진 항목은 자동 배포하지 않고 검토 대상으로 보낸다.

Harness²가 보여준 것은 모델보다 실행 구조의 영향이다

Google Research의 Harness²는 모델 가중치를 바꾸지 않고 에이전트 주변의 실행 구조를 수정한다. 시스템 프롬프트, 가드레일, 메모리, 도구 안내, 서브에이전트, 스킬, 스크립트, 플러그인이 편집 대상이다.

현재 하니스를 실행한 뒤 개선안을 제안하고 후보를 시험해 결과를 비교·조합하는 방식으로 작동한다. 연구진은 WorkBuddy-Bench, JobBench, LAB에서 한 단계의 개선만으로도 성능 상승을 보고했다. 다만 연구 저장소는 공식 Google 제품이 아니며 실행 환경의 네트워크 접근과 샌드박스 설정을 점검해야 한다고 안내한다.

써본 사람들 사이에서는 하니스가 작업별로 좋아질 수 있다는 기대와 함께 특정 테스트에 과적합하거나 컨텍스트를 불필요하게 키울 수 있다는 우려도 나온다. 반복 업무에는 유용하지만 일반화 여부를 별도 테스트하지 않으면 개선처럼 보이는 우연을 배제하기 어렵다는 반응이다.

이 논점은 OpenAPI 전처리에도 적용된다. 에이전트가 스스로 프롬프트와 스킬을 고쳐도 데이터 의미의 정답을 자동으로 만들어내는 것은 아니다. 개선된 하니스는 후보 생성과 검증 순서를 효율화할 수 있지만 도메인 규칙과 승인 기준까지 대신하지는 못한다.

작은 팀이 실제로 만들 수 있는 최소 파이프라인

개인 개발자나 소규모 팀이라면 거대한 데이터 플랫폼보다 다섯 개 산출물부터 정하면 된다. 첫째는 원본 명세와 API 응답이다. 둘째는 기계 검증 로그다. 셋째는 LLM이 만든 매핑 후보와 근거다. 넷째는 사람이 승인한 정제 규칙이다. 다섯째는 정제 결과와 회귀검사 보고서다.

실행 순서도 고정한다. 명세를 읽고 응답을 수집한 뒤 스키마를 검사하고 규칙 기반 변환을 적용한다. 이후 LLM이 의미 후보와 이상값 목록을 만들면 사람이 불확실한 항목을 승인한다. 마지막으로 승인된 규칙을 다시 실행해 결과를 재현한다.

이 방법은 에이전트를 배제하지 않는다. 에이전트는 문서가 부족한 필드를 찾고 샘플을 요약하며 후보 변환을 작성하고 실패 로그를 분류하는 데 쓸 수 있다. 다만 원본 보존, 규칙 검증, 승인 기록, 회귀 테스트는 확률형 모델 바깥에 둬야 한다.

낮은 품질의 OpenAPI 데이터에서 자동화의 한계는 모델의 지능만으로 해결되지 않는다. 데이터의 의미를 결정하는 권한과 그 결정을 재현하는 구조를 함께 설계해야 한다.

자주 묻는 질문

Q

OpenAPI 검증을 통과하면 데이터 품질도 보장되나요?

보장되지 않습니다. OpenAPI 검증은 주로 구조와 타입을 확인하며, 필드의 업무 의미나 실제 응답의 정확성까지 보증하지 않습니다.

Q

LLM으로 데이터 전처리를 자동화할 때 가장 중요한 원칙은 무엇인가요?

원본과 모델 출력을 분리하고, 확정 규칙과 의미 추정을 나눠야 합니다. 불확실한 결과는 자동 반영하지 말고 사람의 검토 목록으로 보내야 합니다.

Q

Harness²는 OpenAPI 데이터 정제 도구인가요?

아닙니다. Harness²는 모델 주변의 프롬프트, 도구, 메모리, 스킬 등을 개선하는 연구 프레임워크입니다. 데이터 정제 파이프라인의 실행 구조를 설계할 때 참고할 수 있지만, 데이터의 의미를 보증하지는 않습니다.
