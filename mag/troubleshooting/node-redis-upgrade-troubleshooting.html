Node 버전 업그레이드 뒤 Redis 장애, 원인부터 복구까지

Node.js 업데이트 후 Redis가 끊겼다면 클라이언트·네이티브 모듈·TLS를 어떤 순서로 점검해야 하는지 정리했다.

2026-10-31논의 1회 정리

Node.js를 올린 직후 Redis 장애가 시작되면 런타임 자체를 의심하기 쉽다. 하지만 실제 원인은 Redis 서버보다 클라이언트 버전, 네이티브 모듈, TLS 설정, 재연결 정책에 숨어 있을 때가 많다. 이 글은 업그레이드 직후 무엇을 먼저 되돌리고 어떤 로그와 파일을 비교해야 원인을 좁힐 수 있는지 답한다.

장애 직후에는 Node 버전부터 고정한다

가장 빠른 첫 조치는 장애가 없던 Node.js 버전으로 실행 환경을 되돌리는 일이다.

다만 롤백은 해결책이 아니라 원인 범위를 줄이는 실험으로 써야 한다. 같은 코드와 같은 Redis 서버를 유지한 채 Node 버전만 바꿔 연결 결과를 비교한다.

Node.js 공식 릴리스 표에 따르면 2026년 10월 31일 기준 v26과 v24는 LTS이며 v27은 Alpha 단계다. 운영 서비스는 Active LTS 또는 Maintenance LTS를 사용하라는 안내가 있다. 새 Current나 Alpha 릴리스를 운영에 바로 넣었다면 먼저 지원 정책과 의존 패키지의 호환 범위를 확인해야 한다. (nodejs.org)

복구 과정에서는 package.json, package-lock.json 또는 pnpm-lock.yaml, Dockerfile, 배포 환경의 Node 버전을 함께 보관한다. node --version, npm ls redis ioredis, npm ls 결과를 장애 전후로 비교하면 런타임 변경과 의존성 변경을 분리할 수 있다.

ioredis와 node-redis의 연결 방식부터 비교한다

Redis 공식 문서는 새 JavaScript 프로젝트에 node-redis를 권장한다. 기존 프로젝트에서 많이 쓰인 ioredis도 지원되지만 두 클라이언트는 연결 시점과 재연결 설정이 다르다. ioredis는 인스턴스를 만들 때 연결을 시작한다. node-redis는 connect()를 명시적으로 호출해야 한다. (redis.io)

이 차이는 초기화 순서가 중요한 애플리케이션에서 장애로 나타난다. 서버가 HTTP 요청을 받기 전에 Redis 연결을 보장하는지, connect() 실패를 어디서 처리하는지, 연결되지 않은 클라이언트에 명령을 쌓는지 확인해야 한다.

node-redis는 isOpen과 isReady를 구분하므로 소켓이 열렸다는 사실만으로 명령 실행 준비가 끝났다고 판단하면 안 된다. (redis.io)

에러 이벤트도 필수다. node-redis는 오류 리스너가 없으면 연결 오류가 처리되지 않은 이벤트로 남아 Node.js 프로세스가 종료될 수 있다고 안내한다. error, connect, ready, reconnecting, end를 구조화된 로그로 남기면 “Redis가 죽었다”는 한 문장을 연결 거부, 타임아웃, 재연결 반복으로 나눌 수 있다. (redis.io)

써본 사람들 사이에서는 두 클라이언트의 선택이 기능보다 운영 경험에 좌우된다는 반응도 있다. 어떤 팀은 ioredis의 자동 재연결과 클러스터 동작을 편하게 느낀다. 다른 팀은 공식 유지보수와 최신 Redis 기능을 이유로 node-redis를 택한다. 기존 서비스라면 장애 직후 클라이언트 교체까지 함께 진행하기보다 먼저 현재 라이브러리의 설정과 버전을 고정하는 편이 안전하다.

Node 업그레이드가 네이티브 모듈을 깨뜨리는 경우

Redis 클라이언트 자체가 순수 JavaScript라면 Node 버전 변경이 곧바로 Redis 프로토콜 장애를 뜻하지는 않는다. 그러나 애플리케이션의 다른 의존성이 네이티브 애드온을 포함하면 이야기가 달라진다. Node.js는 네이티브 애드온의 ABI 버전을 관리하며 V8이나 Node C++ API에 직접 의존하는 모듈은 주요 버전 변경 뒤 재빌드가 필요할 수 있다. (github.com)

npm install이 성공했다는 사실만으로도 충분하지 않다.

사전 빌드 바이너리를 받지 못해 로컬 환경에서 다른 바이너리를 사용하거나 배포 이미지에 이전 build/Release/*.node 파일이 남을 수 있다. npm rebuild, 의존성 캐시 삭제, 새 이미지에서 클린 설치를 각각 시험하고 결과를 비교해야 한다.

재빌드가 필요한 패키지에는 node-gyp가 관여한다. 공식 문서의 node-gyp rebuild는 기존 빌드를 정리하고 configure와 build를 다시 수행하는 절차다. 이 과정에는 Node 헤더, Python, C/C++ 컴파일러가 필요하므로 개발자의 노트북과 운영 컨테이너의 도구 체인이 다르면 결과도 달라진다. (github.com)

Node-API를 사용하는 애드온은 ABI 안정성을 목표로 한다. 그렇다고 외부 라이브러리나 Node C++ API를 직접 사용하는 모듈까지 자동으로 안전해지는 것은 아니다. 장애 로그에 MODULE_NOT_FOUND, NODE_MODULE_VERSION, .node, ERR_DLOPEN_FAILED가 보이면 Redis 설정을 바꾸기 전에 네이티브 의존성 목록부터 확인해야 한다. (nodejs.org)

TLS와 연결 옵션은 주소보다 먼저 검증한다

Node 버전을 바꾼 뒤 Redis 연결이 ECONNRESET, ETIMEDOUT, 인증 실패로 나타난다면 TLS 설정을 분리해 확인한다. Redis 서비스가 TLS를 요구하면 rediss:// URL이나 클라이언트의 TLS 옵션을 사용해야 한다. node-redis는 소켓 설정에서 TLS와 연결 시간 제한을 지정할 수 있고 ioredis도 tls 옵션과 rediss:// URL을 지원한다. (github.com)

확인 순서는 단순해야 한다. 먼저 호스트와 포트에 TCP 연결이 되는지 본다. 다음으로 인증서 체인, SNI의 서버 이름, CA 파일, 인증 정보를 확인한다. 마지막으로 클라이언트가 실제로 사용하는 URL과 옵션을 로그에 남긴다.

비밀번호나 인증서 내용은 기록하지 말고 redis인지 rediss인지와 TLS 사용 여부만 남긴다.

Redis 공식 오류 가이드는 ECONNREFUSED, ETIMEDOUT, ECONNRESET, EAI_AGAIN을 재시도나 폴백을 검토할 수 있는 연결 오류로 분류한다. 반면 WRONGTYPE 같은 응답 오류는 네트워크 문제가 아니라 데이터 구조나 코드 문제일 가능성이 높다. 오류 문자열을 한데 묶어 “Redis 장애”로 처리하면 복구 방향이 흐려진다. (redis.io)

재연결은 자동화보다 실패 범위가 중요하다

node-redis는 연결이 끊기면 지수 백오프와 무작위 지연을 섞어 재연결을 시도한다. reconnectStrategy로 재시도 간격과 중단 조건을 바꿀 수 있다. ioredis 역시 retryStrategy를 제공하며 기본 전략은 재시도 횟수에 따라 대기 시간을 늘리고 상한을 둔다. (redis.io)

재연결 뒤에서 요청이 어떻게 기다리는지가 문제다.

연결이 끊긴 동안 명령을 계속 큐에 넣으면 장애가 끝난 뒤 오래된 요청이 한꺼번에 실행될 수 있다. 캐시 조회와 결제·로그인 같은 핵심 경로를 같은 재시도 정책으로 묶지 말고 명령별 타임아웃과 최대 재시도 횟수를 정해야 한다.

Redis를 레이트 리미터에 쓴다면 장애 시 정책도 엔드포인트별로 나눠야 한다. 일반 조회는 짧은 로컬 폴백으로 통과시킨다. 로그인 시도처럼 공격 대상이 되는 경로는 제한 장치가 작동하지 않을 때 차단하는 선택을 검토할 수 있다. 여러 Node 서버가 같은 한도를 공유해야 한다면 카운터를 서버 메모리에 두지 말고 Redis에 둬야 한다.

Redis의 INCR는 원자적으로 카운터를 올리지만 INCR와 EXPIRE를 따로 실행하면 중간 실패로 만료되지 않는 키가 남을 수 있다. Redis 문서는 이 조합을 트랜잭션이나 Lua 스크립트로 묶는 방식을 설명한다. 장애 대응 테스트에서는 정상 재연결뿐 아니라 Redis를 중간에 종료하고 요청 처리와 제한 정책이 의도대로 바뀌는지도 확인해야 한다. (redis.io)

Node 버전 롤백이 연결을 되살렸더라도 “Node가 Redis를 망가뜨렸다”고 단정할 단계는 아니다. 실제 원인은 지원되지 않는 런타임 조합, 재빌드되지 않은 애드온, TLS 옵션 변화, 또는 재연결 큐일 수 있다.

장애 전후의 런타임·lockfile·클라이언트 설정을 한 줄씩 비교할 때 비로소 다음 업그레이드를 안전하게 다시 시도할 수 있다.

자주 묻는 질문

Q

Node.js 업그레이드 뒤 Redis가 끊기면 가장 먼저 무엇을 해야 하나요?

장애가 없던 Node.js 버전으로 임시 롤백하고, 같은 코드와 Redis 서버에서 버전만 바꿔 연결 결과를 비교하세요. 이후 lockfile, Redis 클라이언트, 네이티브 모듈, TLS 설정을 순서대로 확인해야 합니다.

Q

ioredis와 node-redis 중 무엇을 사용해야 하나요?

Redis는 새 프로젝트에 node-redis를 권장합니다. 다만 기존 서비스는 ioredis를 즉시 교체하기보다 현재 설정과 재연결 동작을 먼저 안정화하는 편이 안전합니다.

Q

Redis 연결 오류에서 어떤 로그를 남겨야 하나요?

오류 코드와 이벤트 이름, Node.js 버전, Redis 클라이언트 버전, TLS 사용 여부, 재연결 횟수와 지연 시간을 남기세요. 비밀번호와 인증서 내용은 기록하지 않아야 합니다.
