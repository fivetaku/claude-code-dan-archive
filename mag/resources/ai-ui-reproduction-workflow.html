웹 URL과 UI 자료로 AI 인터랙션 재현하기

URL만 던지는 방식의 한계를 넘어, 실제 코드와 디자인 자료를 함께 전달하는 UI 구현 흐름을 살펴본다.

2026-10-22논의 1회 정리

AI 코딩 에이전트에게 참고 사이트 URL 하나를 주면 비슷한 화면은 만들 수 있다. 하지만 인터랙션의 타이밍과 상태 변화까지 맞추기는 어렵다. 클코단 논의는 이 문제를 Lucian UX/UI Prompt와 공개 UI 자료로 보완하는 방법에서 출발했다. 이 글은 URL만 전달할 때 무엇이 빠지는지, 어떤 자료를 함께 넣어야 결과가 달라지는지, 실제 구현 순서를 설명한다.

URL은 분위기를 보여주지만 동작 명세가 되지 않는다

웹페이지 URL은 색상, 간격, 글꼴, 카드 구조를 살피는 출발점이다. 그러나 에이전트가 모든 페이지의 상태 변화와 애니메이션 의도를 정확히 읽는다는 보장은 없다. 특히 스크롤에 반응하는 요소, 포인터 위치에 따라 변하는 카드, 클릭 뒤 여러 단계로 바뀌는 버튼은 정적인 화면만으로 구현하기 어렵다.

최근에는 웹사이트에서 디자인 토큰과 컴포넌트 정보를 추출해 코딩 에이전트에 전달하는 도구도 등장했다. Layout은 라이브 웹사이트에서 토큰, 컴포넌트, 폰트, 스크린샷을 추출한 뒤 layout.md나 MCP를 통해 에이전트에 제공한다. URL을 보여주는 데서 끝나지 않고 색상·간격·컴포넌트 규칙을 별도의 구조화된 문서로 바꾸는 방식이다. (layout.design)

방 논의에서도 URL만 전달했을 때보다 관련 UI/UX 자료를 폴더째 내려받아 함께 참조시키면 애니메이션 재현이 나아졌다는 의견이 많았다. URL은 최종 답안이 아니라 관찰 대상으로 보는 편이 정확하다.

Lucian UX/UI Prompt는 실행 가능한 기준점을 만든다

Lucian UX/UI Prompt는 버튼, 입력창, 메뉴, 차트 같은 인터페이스 요소 200개를 제공한다. 공식 갤러리에서는 각 요소를 자동으로 시연하거나 직접 조작할 수 있고, 프롬프트와 코드로 가져갈 수도 있다. 2026년 10월 현재 갤러리와 저장소에는 200개 요소가 안내돼 있다. (lucianlabs.dev)

이 프로젝트는 예시 이미지 대신 실행되는 HTML, CSS, JavaScript를 제공한다. 각 요소는 독립된 파일로 관리하고 CSS 선택자는 .uNNN 계열로 범위를 제한한다. 색상에는 --ux-* 토큰을 쓰며, 요소별 자동 시연에는 클릭·호버·드래그·키보드 입력 단계가 기록된다. 에이전트가 화면 모양뿐 아니라 동작 순서도 참고할 수 있다. (github.com)

사용자는 갤러리에서 요소를 먼저 누른 뒤 적용 프롬프트를 복사할 수 있다. 프롬프트에는 프로젝트의 프레임워크와 스타일링 방식을 먼저 확인하고 기존 컴포넌트와 접근성 속성을 보존하며 테마 토큰을 연결하라는 절차가 포함된다. 파일 변경 목록과 확인 범위를 보고하도록 요구하는 점도 일반적인 “비슷하게 만들어줘”와 다르다. (lucianlabs.dev)

실제 구현은 관찰·분리·이식 순서로 진행한다

가장 재현성이 높은 흐름은 다음과 같다. 먼저 참고 페이지 URL을 전달하고 에이전트에게 색상·글꼴·간격·레이아웃·상태 변화를 목록으로 추출하게 한다. 그다음 구현하려는 인터랙션을 하나의 컴포넌트로 좁힌다. 예를 들어 “가격표 전체”가 아니라 “월간·연간 요금 전환 카드”처럼 동작 단위를 분리한다.

두 번째로 Lucian 갤러리에서 유사한 요소를 찾는다. 번호를 지정하거나 npx skills add Seokwoooo/lucian-uxui로 스킬을 설치하면 코딩 에이전트가 라이브러리에서 요소를 검색하고 프로젝트로 옮길 수 있다. 저장소는 정적 데이터를 api/v1/에 제공한다. 로컬에서는 저장소를 내려받은 뒤 node src/build.mjs로 독립 갤러리를 만들 수 있다. (github.com)

세 번째로 공개된 참고 자료를 로컬 폴더에 모은다. 이미지 모음만으로는 부족하다. 관련 HTML·CSS·JavaScript, 디자인 토큰, 애니메이션 설명, 상태별 캡처를 함께 묶어야 한다. 에이전트에는 “이 폴더는 참고 자료이며, 기존 프로젝트의 프레임워크와 파일 구조를 우선한다”고 명시하고 새로 가져올 것과 버릴 것을 구분하게 해야 한다.

마지막으로 에이전트에게 삽입 위치와 교체 대상을 정확히 지정한다. Lucian의 적용 지침처럼 기존 데이터와 이벤트 핸들러를 유지하고 전역 CSS를 건드리지 않으며 실제 서비스 데이터로 샘플 내용을 교체하도록 요구한다. 결과는 화면 캡처만 보지 말고 라이트·다크 테마, 모바일 너비, 키보드 조작, 최종 상태까지 확인해야 한다. (lucianlabs.dev)

애니메이션 자료는 코드와 접근성을 함께 봐야 한다

애니메이션을 그대로 복사해도 항상 좋은 결과가 나오지는 않는다. MDN은 성능을 위해 transform과 opacity처럼 레이아웃을 다시 계산하지 않는 속성을 우선하고 width, height, margin, top, left처럼 기하 구조를 바꾸는 속성은 사용을 줄이라고 설명한다. CSS 애니메이션은 브라우저가 탭의 가시성이나 프레임 갱신을 고려할 여지가 있다는 장점도 있다. (developer.mozilla.org)

접근성도 구현 명세에 포함해야 한다. prefers-reduced-motion은 운영체제나 브라우저에서 움직임을 줄이도록 설정했는지 감지하는 미디어 기능이다. MDN은 큰 이동이나 확대 대신 더 단순한 페이드 같은 대체 애니메이션을 사용할 수 있다고 안내한다. W3C 역시 상호작용으로 시작되는 비필수 애니메이션을 끌 수 있어야 하며 사용자의 동작 선호를 존중하라고 설명한다. (developer.mozilla.org)

Lucian의 적용 프롬프트가 축소 모션 상태에서도 기능과 최종 상태를 확인하라고 요구하는 이유가 여기에 있다. 애니메이션을 제거했을 때 버튼의 완료 표시나 오류 상태까지 사라진다면 시각 효과를 줄인 게 아니라 기능을 잃은 것이다.

자료를 많이 넣는 것보다 역할을 나누는 편이 낫다

AI 코딩 에이전트가 UI를 엉뚱하게 만드는 원인으로는 구조, 문구, 기술 스택을 한 번에 추측하게 만드는 상황이 자주 거론된다. 실사용자들 사이에서도 에이전트가 필요 이상으로 컴포넌트를 추가하거나 프로젝트에 없는 UI 라이브러리를 임의로 불러오거나 원하는 계층 구조와 다른 화면을 만든다는 반응이 있다. UI 입력을 더 많이 넣기보다 입력마다 역할을 나눠야 한다는 뜻에 가깝다. (reddit.com)

URL은 전체 분위기와 화면 관계를 설명한다. Lucian 요소는 재현할 인터랙션의 작동 예시가 된다. 내려받은 폴더는 세부 스타일과 상태별 참고 자료가 된다. 프로젝트 파일은 실제 데이터와 기존 규칙을 제공한다. 네 자료를 한 덩어리로 붙이지 말고 각각의 우선순위를 지정하면 에이전트가 참고 자료를 제품 코드로 오인할 가능성을 줄일 수 있다.

개인 개발자나 소규모 팀에게 이 방식의 장점은 디자인 시스템을 새로 문서화하는 시간을 줄이는 데 있다. 다만 결과물은 자동 생성보다 이식 작업에 가깝다. 원본의 구조와 움직임을 보존하되 현재 프로젝트의 컴포넌트 경계·테마 변수·접근성 요구에 맞춰 바꾸는 과정이 필요하다.

URL만 던지는 방식은 빠르지만 정교한 인터랙션을 만들기에는 정보가 부족하다. 실행 가능한 UI 요소와 로컬 참고 자료를 함께 제공하면 에이전트가 무엇을 닮아야 하는지뿐 아니라 무엇을 어떻게 움직여야 하는지도 판단할 수 있다. 앞으로의 질문은 “AI가 이 화면을 만들 수 있나”보다 “어떤 동작 명세를 어떤 형식으로 넘겨야 같은 화면이 다시 나오나”에 가까워질 것이다.

자주 묻는 질문

Q

AI 코딩 에이전트에게 웹사이트 URL만 보내도 UI를 재현할 수 있나요?

기본 레이아웃과 색상은 재현할 수 있지만, 상태 변화와 애니메이션까지 정확히 맞추기는 어렵습니다. 실행 코드, 디자인 토큰, 상태별 참고 자료를 함께 제공하는 편이 낫습니다.

Q

Lucian UX/UI Prompt는 어떻게 사용하나요?

갤러리에서 요소를 직접 확인한 뒤 프롬프트나 코드를 복사하면 됩니다. 에이전트에서 쓰려면 npx skills add Seokwoooo/lucian-uxui로 스킬을 설치할 수 있습니다.

Q

애니메이션을 구현할 때 반드시 확인할 항목은 무엇인가요?

라이트·다크 테마, 모바일 너비, 키보드 조작, 최종 상태, prefers-reduced-motion 대응을 확인해야 합니다. 성능을 위해 transform과 opacity 중심으로 설계하는 것도 중요합니다.
