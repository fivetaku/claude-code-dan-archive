Railway 콜백 배포, 고정 IP가 필요한 경우와 설정법

콜백을 받는 주소와 외부 API를 호출하는 주소는 다르다. 로컬 서버를 클라우드로 옮길 때 필요한 배포 순서와 유료 플랜의 조건을 짚는다.

2026-11-01논의 1회 정리

서비스 심사를 기다리는 동안 개발용 컴퓨터를 꺼도 될까. 클코단에서는 로컬 서버를 유지해야 했던 경험과 IP 등록 조건 때문에 Railway 유료 상품을 선택했다는 사례가 공유됐다. 이 사례에서 풀어야 할 질문은 하나다. 콜백 서버를 클라우드로 옮길 때 필요한 것은 지속적인 실행 환경인가, 고정 IP인가, 아니면 둘 다인가.

콜백 수신 주소와 API 발신 IP는 다르다

방에서 언급된 연동 서비스와 심사 규정은 구체적으로 확인되지 않았다. 그러므로 해당 사례를 모든 콜백의 공통 조건으로 확대할 수는 없다. 특히 외부 요청을 받는 주소와 내 서버가 요청을 보낼 때 사용하는 주소를 구분해야 한다.

Railway 공식 문서에서 Public Networking은 HTTP·HTTPS 요청을 받는 기능이다. 제공 도메인이나 사용자 도메인을 연결하고 SSL 인증서를 자동으로 적용한다. 반면 Static Outbound IPs는 서비스가 외부 시스템에 접속할 때 사용하는 발신 IPv4를 고정한다. 이 주소로 외부 요청을 받을 수는 없다. (docs.railway.com)

가령 상대 서비스가 이벤트를 전달할 HTTPS URL을 요구한다면 공개 도메인과 수신 경로가 대응 대상이다. 상대 API가 접속자의 IP를 허용 목록에 등록하라고 한다면 발신 IP가 대응 대상이다. 상대가 수신 서버의 목적지 IP까지 고정하라고 요구하는 경우에도 Railway의 발신 IP 기능으로 대체할 수 없다. 기능의 방향을 나누면 같은 ‘IP 등록’이라는 표현에서 생기는 혼동을 줄일 수 있다. (docs.railway.com)

따라서 방의 유료 전환 경험은 특정 연동 조건을 해결한 사례로 읽어야 한다. 콜백이라는 이름만으로 유료 고정 IP가 필수라고 판단할 근거는 없다.

로컬 컴퓨터 대신 무엇을 계속 실행해야 하나

GitHub 공식 문서는 웹훅 URL에 localhost나 127.0.0.1을 사용할 수 없다고 설명한다. 로컬 테스트에는 전달 서비스를 이용할 수 있지만 로컬 서버와 전달 프로그램을 실행해야 한다. 방에서 나온 전원 유지의 부담은 이런 구성에서 충분히 발생한다. 다만 해당 사례가 어떤 전달 도구를 사용했는지는 확인되지 않았다. (docs.github.com)

핵심은 컴퓨터 자체가 아니라 요청을 처리할 프로그램이 살아 있어야 한다는 점이다.

Railway로 애플리케이션을 옮기면 실행 장소를 개인 컴퓨터에서 클라우드 서비스로 바꿀 수 있다. 그러나 클라우드에 배포했다는 사실만으로 모든 요청이 즉시 처리되지는 않는다. Railway의 Serverless 문서는 잠든 서비스를 깨우는 첫 요청에 지연이 생기며 502 응답이 발생할 수도 있다고 명시한다. 심사 요청처럼 도착 시간을 통제하기 어렵다면 절전 설정도 검토 대상이다. (docs.railway.com)

비용 제한 역시 가용성과 연결된다. Railway의 Hard limit은 단순 경고가 아니라 사용량이 한도를 넘으면 워크로드를 중지하는 장치다. 심사용 서버의 예산을 설정할 때는 알림과 강제 중단을 같은 기능으로 취급하면 안 된다. (docs.railway.com)

Railway에 수신 서버와 데이터베이스를 연결하는 순서

공식 SaaS 배포 가이드를 기준으로 하면 재료는 애플리케이션 저장소, 실행 명령, 필요한 데이터베이스다. 새 프로젝트에 GitHub 저장소를 연결해 API 서비스를 배포하고 저장할 데이터가 있다면 PostgreSQL 서비스를 추가한다. 애플리케이션의 DATABASE_URL에는 PostgreSQL 서비스의 연결 변수를 참조하도록 설정한다. 연결 문자열을 코드에 직접 적을 필요는 없다. (docs.railway.com)

다음은 프로그램이 요청을 받는 위치다. Railway 문제 해결 문서는 서버를 0.0.0.0에 바인딩하고 플랫폼이 제공하는 PORT 값으로 실행하도록 안내한다. 서비스가 시작돼도 다른 포트를 듣고 있다면 공개 주소로 접근할 때 실패할 수 있다. (docs.railway.com)

서비스 설정의 Networking에서 Public Networking을 열고 Generate Domain을 선택한다. 생성된 HTTPS 주소에 애플리케이션이 구현한 콜백 경로를 붙여 연동 서비스에 등록한다. 여기서 산출물은 단순한 배포 완료 표시가 아니라 외부에서 실제 요청을 보낼 수 있는 수신 URL이다. (docs.railway.com)

입력과 결과도 구분해 시험해야 한다. 테스트 이벤트를 전송한 뒤 상대 서비스의 전달 기록과 서버 로그를 대조하고 저장 로직이 있다면 데이터베이스 반영까지 확인한다. GitHub 문서는 이벤트가 생성됐는지부터 확인한 다음 DNS, 연결, 응답 지연을 나눠 진단한다. Railway에서는 배포 로그와 HTTP 로그를 각각 조회할 수 있다. (docs.github.com)

Pro가 필요한 조건과 직접 임대의 비교 기준

Railway의 Static Outbound IPs는 Pro에서 제공된다. 공식 절차는 서비스 Settings의 Networking에서 Enable Static IPs를 켜고 배정 주소를 확인한 뒤 재배포하는 방식이다. 현재 문서는 서비스에 세 IPv4를 배정해 트래픽을 분산한다고 설명한다. 상대 시스템의 허용 목록도 실제 배정된 주소 전체를 반영해야 한다. (docs.railway.com)

고정과 전용은 다르다. Railway는 해당 주소가 다른 고객과 공유될 수 있으며 서비스 리전을 변경하면 주소도 달라진다고 명시한다. 상대가 독점적으로 사용하는 IP를 요구한다면 단지 ‘고정 IP 지원’이라는 항목만으로 적합성을 판단할 수 없다. (docs.railway.com)

공식 요금 안내에서 Hobby는 월 5달러, Pro는 월 20달러의 최소 사용 약정이다. 각각 같은 금액의 사용량이 포함되며 초과분은 추가된다. 작은 팀에는 트래픽보다 연동 조건 때문에 최소 비용이 달라질 수 있다는 점이 중요하다. 서버 규모가 작더라도 발신 IP 허용 목록이 필요하면 플랜 선택에 영향을 준다. (docs.railway.com)

써본 사람들 사이에서는 배포와 PostgreSQL 연결의 편리함을 높게 평가하면서도 직접 운영하는 VPS와 비용을 비교해야 한다는 의견이 나온다. 이는 사용 경험에 따른 평가이며 동일한 부하에서 검증한 가격 비교는 아니다. (reddit.com)

방에서는 가비아 서버 임대에 중계기를 붙이는 방식도 비교 대상으로 제시됐다. 다만 구성 파일이나 전달 경로가 없어 재현 가능한 구현 사례로 소개하기는 어렵다. GitHub 공식 문서가 설명하는 일반적인 역방향 프록시는 외부 요청을 받아 내부 애플리케이션으로 전달한다. 중계 서버를 세웠다는 사실만으로 뒤쪽 애플리케이션의 실행 조건까지 없어지는 것은 아니다. (docs.github.com)

고정 IP 이후에도 남는 콜백 실패 원인

주소를 고정해도 응답이 늦으면 전달은 실패할 수 있다. GitHub는 웹훅을 받은 뒤 10초 안에 2xx 응답을 보내도록 요구한다. 오래 걸리는 작업은 큐로 넘겨 비동기로 처리하라고 안내한다. 이 제한은 GitHub의 규칙이며 방에서 사용한 미상의 서비스에도 같다고 가정해서는 안 된다. (docs.github.com)

Railway의 공식 구성 예시는 수신 API가 서명을 검증하고 Redis에 작업을 넣은 뒤 응답하도록 나눈다. 별도 워커가 큐에서 작업을 가져가 처리한다. 요청을 받는 순간과 실제 업무를 끝내는 순간을 분리하면 긴 처리 때문에 수신 응답까지 늦어지는 구조를 피할 수 있다. (docs.railway.com)

실패 이후의 복구도 자동이라고 가정할 수 없다. GitHub는 실패한 웹훅을 자동 재전송하지 않는다고 명시하며 수동이나 코드로 재전달하도록 안내한다. 고정 IP는 주소 조건을 해결하지만 전달 누락과 복구까지 해결하는 기능은 아니다. (docs.github.com)

이번 사례에서 배포 결정을 가르는 기준은 ‘로컬인가 클라우드인가’만이 아니다. 수신 URL을 유지하려는지, 외부 API에 제출할 발신 주소를 고정하려는지부터 요구사항이 갈린다. 두 목적을 섞으면 비용을 올리고도 원래의 콜백 문제는 남을 수 있다.

자주 묻는 질문

Q

Railway에서 콜백을 받으려면 고정 IP가 필수인가요?

공개 HTTPS URL로 받는 요청과 발신 IP 허용 목록은 별개입니다. Railway의 Static Outbound IPs는 외부 API에 접속할 때 사용하는 주소이며, 콜백을 받는 주소로 사용할 수 없습니다. (docs.railway.com)

Q

Railway 고정 IP는 어떤 플랜에서 제공하나요?

공식 문서상 Pro에서 제공합니다. 설정에서 활성화한 뒤 배정 주소를 확인하고 재배포해야 하며, 리전을 변경하면 IP도 바뀝니다. (docs.railway.com)

Q

Railway에 배포하면 개인 컴퓨터를 꺼도 되나요?

요청 처리에 필요한 API와 데이터베이스 등을 클라우드로 옮겼다면 개인 컴퓨터에서 실행할 필요는 없습니다. 다만 Serverless의 초기 응답 지연과 사용량 한도에 따른 서비스 중지는 별도로 고려해야 합니다. (docs.railway.com)
