AI 모델·프롬프트

AI 생성 속도 저하, 모델 문제인지 서비스 문제인지 구별하는 법

Claude·GPT·Antigravity가 느려졌을 때 체감만으로 결론 내리지 않고 원인과 대응을 나누는 방법

2026-11-12논의 1회 정리

AI 코딩 도구를 쓰다 보면 어느 날 갑자기 답변이 늦고, 토큰이 끊겨 나오며, 작업 완료까지 걸리는 시간이 길어진다. 클코단에서도 Claude와 Antigravity를 시작으로 GPT와 Codex까지 비슷한 체감이 이어졌지만, 사람마다 느린 정도는 달랐다. 이 글은 느려진 AI가 모델 자체의 문제인지, 서비스 혼잡인지, 에이전트 구조 때문인지 구분하는 방법을 다룬다.

먼저 ‘느리다’를 세 구간으로 나눠야 한다

AI 응답 속도는 한 숫자로 설명되지 않는다. NVIDIA는 첫 토큰까지 걸리는 시간인 TTFT, 토큰 사이 간격인 TPOT 또는 ITL, 전체 응답 완료 시간인 E2E latency를 별도 지표로 구분한다. 화면에 첫 글자가 늦게 나타나는지, 글자가 나타난 뒤 끊기는지, 마지막까지 끝나는 시간이 긴지를 나눠 봐야 한다. (developer.nvidia.com)

예를 들어 TTFT만 늘었다면 대기열, 긴 입력을 읽는 prefill, 네트워크 지연을 의심할 수 있다. 첫 글자는 빨리 나오지만 이후 생성이 느리다면 모델의 출력 처리량이나 서버의 동시 요청 부담이 더 가까운 원인이다. 전체 작업만 길어졌다면 모델이 코드를 작성하는 시간보다 파일 검색, 테스트 실행, 도구 호출이 늘었을 가능성도 있다.

방 논의에서 언급된 TPS 하락은 유용한 단서지만, 그 자체로 장애 증거는 아니다. 같은 모델도 입력 길이, 출력 길이, 요금제, 요청 시점에 따라 체감 속도가 달라진다.

최근 장애 기록은 ‘느낌’이 실제 현상일 수 있음을 보여준다

서비스 제공업체의 상태 기록을 보면 속도 저하는 단순한 착각으로만 치부하기 어렵다. OpenAI는 ChatGPT와 API에서 대규모 요청 실패가 발생한 사례를 설명했고, 원인으로 라우팅 계층의 메모리 한계와 용량 부족을 들었다. 2026년 9월 29일에는 기능 배포가 내부 네트워크 트래픽을 과도하게 늘려 ChatGPT와 Codex, API에 오류와 지연이 나타났다고 밝혔다. (status.openai.com)

Anthropic도 2026년 11월 8일 Claude Fable 5.1 요청에서 성능 저하를 공지했다. 해당 기록에는 claude.ai뿐 아니라 Claude API와 Claude Code가 영향 범위로 포함됐다. 11월 10일에는 특정 모델 요청에서 오류가 짧게 발생했다는 기록도 남아 있다. 다만 이 기록만으로 클코단에서 느꼈던 모든 지연이 같은 장애였다고 단정할 수는 없다. (anthropic.statuspage.io)

공식 상태 페이지에 장애가 없는데도 느릴 수 있다. 상태 페이지는 전체 서비스의 평균적인 이상을 보여주지만, 특정 모델·지역·계정 등급·기능 조합의 지연까지 모두 드러내지는 않는다. OpenAI도 개별 고객의 가용성이 요금제와 모델, API 기능에 따라 달라질 수 있다고 안내한다. (status.openai.com)

Antigravity가 특히 느리게 느껴지는 이유

Antigravity는 단순히 한 번 질문하고 한 번 답하는 채팅 도구가 아니다. Google 문서에 따르면 Agent는 기존 코드를 읽고, 도구를 사용하고, 결과물을 만들며, 여러 대화를 병렬로 운영할 수 있는 다단계 시스템이다. 따라서 화면에 답변이 나타나기 전에도 계획 수립, 파일 탐색, 터미널 실행, 검증 과정이 진행될 수 있다. (antigravity.google)

이 구조에서는 모델의 TPS가 빨라도 작업 전체가 빨라지지 않는다. Microsoft Research는 에이전트 작업에서 도구 호출이 최종 응답이 보이기 전까지 걸리는 시간의 30~80%를 차지할 수 있다고 분석했다. 여러 호출을 순서대로 실행하면 각각의 대기 시간이 누적되고, 같은 저장소를 반복해서 읽는 과정에서 캐시 효율도 떨어질 수 있다. (microsoft.com)

Antigravity 공식 문서도 목표 모드가 작업 완료 여부를 확인하고, 하위 작업이 끝날 때까지 기다리며, 테스트나 빌드 같은 증거를 요구한다고 설명한다. 사용자가 짧은 코드 수정으로 생각한 요청을 에이전트가 검토와 검증을 포함한 장기 작업으로 해석하면, 일반 채팅보다 느린 것이 이상하지 않다. (antigravity.google)

실사용자 사이에서는 Antigravity가 작은 수정에도 저장소를 넓게 읽거나 여러 단계를 거쳐 답답하다는 반응이 나온다. 반대로 작업을 작게 나누고 한 번에 한 단계씩 요청하면 충분히 쓸 만하다는 의견도 있다. 이 차이는 모델 성능보다 에이전트가 수행하는 작업 경로에서 생길 수 있다.

속도 진단 절차

첫 번째로 같은 프롬프트를 준비한다. 짧은 코드 설명, 20줄 안팎의 수정 요청, 긴 저장소 분석 요청을 각각 하나씩 만들고 같은 모델과 같은 계정에서 여러 번 실행한다. 결과를 비교할 때는 답변 품질보다 TTFT, TPOT, 전체 완료 시간을 따로 기록한다.

두 번째로 입력을 줄여 본다. 긴 대화와 저장소 전체를 붙인 요청이 느리고 짧은 새 대화가 빠르다면, 모델이 느려졌다기보다 컨텍스트 처리 비용이 커졌을 가능성이 높다. OpenAI는 긴 출력을 줄이고, 반복되는 입력을 캐시하며, 가능한 경우 Predicted Outputs를 활용하는 방식을 지연 최적화 방법으로 안내한다. (developers.openai.com)

세 번째로 도구를 끈 요청과 켠 요청을 비교한다. 파일 검색이나 테스트 실행이 없는 단순 생성은 빠른데 에이전트 작업만 늦다면, 도구 호출과 오케스트레이션에 걸리는 시간을 따로 확인한다. 연구에서도 계획·검색·도구를 결합한 에이전트가 단일 호출보다 정확해질 수 있지만, 사례에 따라 지연 시간이 수 초에서 수백 초까지 늘어날 수 있다고 보고했다. (arxiv.org)

마지막으로 같은 시간대에 다른 모델과 서비스를 비교한다. Claude, GPT, Codex, DeepSeek, Qwen처럼 대안을 번갈아 쓰는 것은 장애 우회에는 도움이 되지만, 결과 품질과 사용 한도까지 함께 바뀐다. 방에서 일부 참여자가 모델을 바꿔 보려 했던 경험도 이 지점과 맞닿아 있다. 다만 모델을 바꿨더니 빨라졌다는 사실만으로 기존 서비스의 공식 장애를 입증할 수는 없다.

개인 개발자에게 중요한 것은 평균 속도보다 작업당 대기 시간이다

개인 개발자나 소규모 팀은 ‘초당 토큰 수’만 보고 도구를 고르면 안 된다. 짧은 코드 보완은 TTFT와 TPOT가 중요하지만, 테스트와 파일 수정이 포함된 에이전트 작업은 도구 호출 횟수와 검증 단계가 더 큰 영향을 준다. Google도 Gemini API에서 표준 처리, 우선 처리, 배치 처리, 캐시를 작업 성격에 맞춰 선택하도록 안내한다. 우선 처리는 지연을 낮추고 신뢰성을 높이는 대신 표준 요금보다 비싸고, Flex나 Batch는 비용을 낮추지만 즉시 응답에는 적합하지 않다. (ai.google.dev)

실무에서는 요청을 세 종류로 나누는 편이 낫다. 즉시 답이 필요한 작은 수정은 빠른 모델과 짧은 컨텍스트를 사용하고, 저장소 전체를 읽어야 하는 작업은 기다릴 시간을 감안해 목표와 검증 조건을 명확히 적는다. 반복되는 분석은 캐시나 고정된 작업 흐름으로 줄이고, 불필요한 재시도는 중단한다.

클코단의 체감처럼 여러 AI 도구가 동시에 느려졌다면 서비스 공급자의 장애나 공용 인프라 혼잡을 먼저 확인할 이유가 있다. 반대로 특정 프로젝트에서만 느리고 새 대화나 짧은 요청은 정상이라면 컨텍스트와 에이전트 경로를 먼저 봐야 한다. 느림을 하나의 감상으로 묶지 않고 TTFT·TPOT·도구 호출로 쪼개는 순간, 모델을 무작정 갈아타지 않고 무엇을 줄여야 하는지 판단할 수 있다.

자주 묻는 질문

Q

AI 답변이 느려졌을 때 가장 먼저 확인할 것은 무엇인가요?

첫 토큰까지의 시간, 토큰 사이 간격, 전체 완료 시간을 나눠 기록하세요. 공식 상태 페이지에서 장애를 확인한 뒤 짧은 프롬프트와 긴 프롬프트를 비교하면 원인 범위를 좁힐 수 있습니다.

Q

Antigravity는 왜 일반 채팅보다 느릴 수 있나요?

Antigravity는 코드 탐색, 파일 수정, 터미널 실행, 테스트 같은 여러 단계를 수행하는 에이전트입니다. 모델 생성 속도보다 도구 호출과 검증 단계가 전체 시간을 더 크게 늘릴 수 있습니다.

Q

모델을 바꾸면 AI 속도 문제가 해결되나요?

서비스 장애나 특정 모델의 혼잡이라면 도움이 될 수 있습니다. 다만 품질, 사용 한도, 컨텍스트 처리 방식도 함께 바뀌므로 같은 프롬프트를 여러 번 비교해야 합니다.
