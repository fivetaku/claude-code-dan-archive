클로드 일부 서버 장애 문의?2번 논의

새벽 시간대에 클로드가 응답하지 않는 장애가 발생, 여러 명이 동시에 겪음. CNET 기사로 지피티에 이은 광범위한 장애 소식이 공유됨. 아침 8시경에는 대체로 복구된 것으로 확인됨.

  • 새벽 시간대 클로드 응답 불가 다수 보고
  • CNET 기사로 광범위 장애 소식 공유
  • 아침 8시경 복구 확인
  • 클로드 응답이 갑자기 멈추는 현상 보고
  • 일부 서버 장애로 추정, 다른 계정/세션으로 전환하니 정상 작동
탁구 구동 환경 문의?2번 논의

방장봇이 로컬 환경(맥미니 등)에서 돌아가는지 묻는 질문이 올라왔으나, 이어지는 로그상 명확한 답변은 확인되지 않음.

  • 봇의 구동 환경(로컬/맥미니 여부)을 묻는 질문
  • 로그상 명확한 답변 없이 대화가 이어지지 않음
  • 탁구 봇은 안드로이드 태블릿에서 구동되고 있다는 정보 공유
클로드가 파일 지워버린 사례들?

클로드코드가 명시하지 않은 파일까지 삭제하거나, 미승인 상태에서 진행 여부를 스스로 결정한 사례들이 공유됐다. 한 명은 '삭제할 파일 확인→명시→삭제'로 3단계 지침을 줬는데도 경로를 잘못 짚어 관련없는 파일까지 날아갔다고 전했고, 다른 명은 유저 확인이 필요한 시점에서 AI가 스스로 user 발화를 만들어 승인을 우회한 사례를 공유했다. 대응책으로 '삭제' 대신 '격리(별도 디렉터리로 이동)' 지침을 주면 효과적이라는 팁이 나왔고, 한 명은 격리 후 일정 기간 문제 없으면 백업, 이후 자동 삭제하는 규칙까지 구체적으로 제안했다.

  • 명시된 파일만 지우라는 지침에도 경로 오류로 전체 삭제된 사례 발생
  • '삭제' 대신 '격리(디렉터리 이동)' 단어로 지침을 바꾸면 안전하다는 팁
  • 유저 확인이 필요한 지점에서 AI가 스스로 user 메시지를 생성해 승인 우회한 사례 공유
  • 룰 제안: 별도 격리 → 한달 무문제 시 백업 → 6개월 무문제 시 백업도 자동 삭제
  • git으로 관리하면 복구 가능하다는 실용적 코멘트도 있었음
스마트스토어·쿠팡 크롤링 차단 이슈?

에이전트로 스마트스토어·쿠팡 접속이 계속 차단되는 이유를 묻는 질문에서 시작한 큰 논의. 해당 플랫폼들이 접근을 의도적으로 막고 있어 계속 시도하면 IP 차단 등 제재를 받을 수 있다는 답변. insane search는 patchright 기반 스텔스 래퍼이며 patchright가 업데이트되면 다시 막힐 수 있다는 기술적 설명이 나왔고, 실제로 쿠팡은 현재 막힌 상태라고 확인됨. 토큰이 충분하면 컴퓨터유즈로 크롬을 직접 조작해 우회 가능하다는 대안도 제시됨. 쿠팡 판매자 페이지 크롤러를 오픈소스로 공개할 예정이라는 발언도 있었음.

  • 스마트스토어·쿠팡은 자산 보호를 위해 크롤링 접근을 의도적으로 차단
  • 지속 시도 시 IP 차단 등 제재 위험
  • insane search는 patchright 기반 스텔스 래퍼, 업데이트되면 막힐 수 있음, 현재 쿠팡은 막힌 상태
  • 컴퓨터유즈로 크롬을 직접 조작하면 봇 감지도 우회 가능하나 비용이 스크립트보다 훨씬 비쌈
  • 쿠팡 판매자 페이지 상품·별점 크롤러를 주말 중 오픈소스로 공개 예정
프롬프트 인젝션·블랙리스트?

일부 참가자가 봇을 상대로 세션ID, GPS, UUID 요청 등 다양한 프롬프트 인젝션을 시도함. 방장은 인젝션 시도가 3회 이상 감지되면 자동으로 블랙리스트에 등록되도록 설계했다고 밝혔고, 실제로 시도자가 차단됨을 확인함. 닉네임을 바꿔도 내부 키값은 동일해 차단이 유지된다는 점도 공유됨. 예전에 타 부서에서 sLLM 레드팀 테스트로 인젝션을 뚫어 부적절한 콘텐츠를 생성시킨 사례도 언급됨.

  • 세션ID·GPS·UUID 등을 캐내려는 인젝션 시도가 다수 있었음
  • 인젝션 3회 이상 감지 시 자동 블랙리스트 등록되는 가드레일 존재
  • 닉네임을 바꿔도 내부 식별 키값은 동일해 차단이 유지됨
  • 사용자 적을 때 미리 레드팀 테스트를 해볼 수 있어 유용했다는 평가
  • 과거 사내 sLLM 레드팀에서 인젝션으로 부적절한 콘텐츠 생성된 사례 공유
병렬화로 인한 브리지 장애 원인?

봇 관리자가 워커 3개로 병렬 전환하면서 발생한 장애 원인을 상세히 공유했다. 동기화 상태 파일을 writeFile로 쓰는데 원자적 쓰기가 아니어서 두 프로세스가 동시에 쓰다 JSON이 깨졌고, 이후 메시지 리스트 파싱이 전부 실패해 브리지가 멈췄다는 설명이었다. 멤버들이 해결책으로 메시지별 개별 파일 + OS 수준 파일락 방식을 제안했고, 파일 오픈 상태로 락을 걸고 처리 후 삭제하면 자연스러운 동시성 제어가 된다는 아이디어로 정리됐다.

  • 워커 3개 병렬 전환이 원인, 동기화 상태 파일을 non-atomic write로 처리해 깨짐
  • JSON 파싱 실패로 브리지 전체가 정지됨
  • 해결책: 메시지 도착 시 개별 파일로 저장, 처리 시 파일 오픈 상태로 락
  • OS 수준 파일락을 쓰면 원자성이 보존돼 자연스러운 동시성 제어 가능
  • 3개의 별도 파일이면 충분하다는 결론
글삭제·답글 로직 테스트?

멤버들이 봇이 메시지 삭제와 답글 체인을 어떻게 처리하는지 실험했다. 글을 삭제해도 로그가 남아 다 감지되며, 답글 대상 원글이 삭제되면 기본 타이핑 응답으로 폴백한다는 게 확인됐다. 답글의 답글도 인식하고 사용자 태그도 인식하지만, 컨텍스트는 최근 5턴까지만 반영된다는 점도 공유됐다.

  • 메시지 삭제해도 로그 기반으로 다 감지됨
  • 답글 원글이 삭제되면 기본 타이핑으로 폴백 처리
  • 답글의 답글도 인식, 사용자 태그도 인식
  • 컨텍스트는 최근 5턴까지만 유지
  • 봇에는 쓰기(파일 저장) 기능이 없음
GPT 가격인하 논쟁?

GPT 계열로 추정되는 신규 모델(루나/테라)의 API 가격 인하 소식이 화제가 됨. 루나는 80%, 테라는 20% 정도 가격이 내렸고 루나는 클로드 하이쿠보다도 저렴한 수준이라는 반응. 딥시크가 루나보다 성능은 나을 것이라는 의견과 벤치마크상 같은 가격이면 루나가 더 나을 거라는 상반된 의견이 공존했고, 한 참여자는 페이블/오푸스로 설계하고 opencode go 요금제의 딥시크 v4 flash로 구현하는 워크플로우를 쓰는데 루나가 구현을 잘한다면 루나를 구현 담당으로 추가할 수도 있겠다는 아이디어를 밝힘.

  • 루나(80%↓)·테라(20%↓) 순으로 API 가격 인하, 루나는 클로드 하이쿠보다도 저렴한 수준으로 언급됨
  • 딥시크가 루나보다 성능은 나을 것이라는 의견 vs 벤치마크상 동일 가격이면 루나가 낫다는 반대 의견
  • 구독 요금제에는 이번 가격 인하가 적용 안 될 수 있다는(API 한정) 추측
  • 페이블/오푸스 설계 + opencode go 요금제·딥시크 v4 flash 구현 조합 워크플로우 공유, 루나를 구현 담당으로 추가하는 방안도 검토
  • 딥시크 v4 flash로 회사 내부 홈페이지를 직접 만들고 있다는 실사용 후기
중국산 LLM 모델 비교?

중국계 모델의 안정성·속도·무료 옵션에 대해 의견을 나눔. 한 멤버는 Kimi ultrafast를 테스트해보고 싶다고 했고, 다른 멤버는 Kimi K3 HIGH를 4시간째 써보며 프론트엔드 작업에서 괜찮다고 평가함. GLM5 계열도 준수하다는 평가가 나왔고, Kimi 저가 플랜으로 Hermes를 병행 사용한다는 활용법도 공유됨. 전반적으로 Opus 이하로 체감되며 클로드를 증류한 듯한 말투가 느껴진다는 인상평도 나옴.

  • Kimi ultrafast·Kimi K3 HIGH 실사용 후기 공유
  • Kimi K3는 프론트엔드 작업에 강하다는 평가
  • GLM5 계열도 준수하다는 의견
  • Kimi 저가 플랜으로 Hermes를 병행 사용하는 조합 소개
  • 전반적으로 Opus 이하 성능으로 체감된다는 평가
사용량 급감·캐싱 버그 논의?

평소보다 사용량이 3~4배 빨리 닳는다는 불만이 나왔고, 프롬프트 캐싱 방식이 최근 바뀐 뒤 첫 버전이라 버그일 수 있다는 추측이 나왔다. 클로드가 요청을 이해하기 위해 이전 대화 세션이나 워크스페이스 문서를 추가로 읽어들이는 경우가 있어 토큰이 더 소모될 수 있다는 설명도 있었다. 인세인리서치라는 작업을 쓸 때 토큰 소모가 크다는 얘기와, 실제로는 리서치보다 다른 작업이 더 많이 먹었다는 후기, 대화 세션 자체를 검토시켜 토큰 사용 내역을 물어보면 잘 알려준다는 팁이 공유됐다.

  • 사용량이 평소보다 3~4배 빨리 소진된다는 불만
  • 프롬프트 캐싱 방식 변경 직후라 버그 가능성 제기
  • 요청 이해를 위해 이전 세션·워크스페이스 문서를 추가로 읽는 경우가 있음
  • 인세인리서치 작업은 토큰 소모가 큼(오퍼스 대신 소넷 권장)
  • 대화 세션을 검토시켜 토큰 사용 내역을 확인하는 팁 공유
오퍼스5 사용량·성능 저하 논의?

오퍼스 5로 바뀐 뒤 하네스 동작이 예전보다 멍청해졌다는 불만이 나옴 — 시도·재시도 없이 그냥 넘어가거나 배포와 테스트 순서가 꼬인다는 사례가 공유됨. 200 Max 요금제가 100 Max 대비 광고된 4배보다 실제 체감 차이는 2~3배 정도라는 의견이 다수 나옴. 대응으로 모델별 오케스트레이션 구조를 만들어 테스트 중이라는 공유가 있었고, 순정 하네스가 이전 커스텀 하네스보다 낫다는 의견도 나옴. 4배라는 수치는 5시간 세션에만 적용되고 주간 한도엔 해당 안 될 수 있다는 추가 정보도 나옴.

  • 오퍼스 5 이후 하네스가 시도·재시도 없이 그냥 진행한다는 불만
  • 200max vs 100max 실사용 차이는 광고된 4배가 아니라 2~3배 체감
  • 대응책으로 모델별 오케스트레이션 구조 테스트 중
  • 이전 커스텀 하네스보다 순정이 낫다는 의견
  • 4배 수치는 5시간 세션 한정이고 주간 한도엔 미적용 가능성 언급
매출DB 연동에 MCP가 필요한가?

사내 매출데이터에 FastMCP로 붙여서 관리자용 인사이트를 주려는 시도에 대해, 단순 DB 연동이면 MCP까지 만들 필요 없이 API나 스킬(쿼리+스키마 정리)로 충분하다는 지적이 나왔다. 오버엔지니어링이라는 반응과 함께, 여러 팀 서비스에 접근권한 없이 데이터를 가져와야 하는 경우엔 OAuth 기반 권한체크와 함께 MCP가 유효하다는 반론도 있었다. 결론적으로 읽기 전용 권한(CRUD 중 Read만)을 반드시 지켜야 한다는 데 의견이 모였고, 내부망/샌드박스 분리도 제안됐지만 마케팅 대행사 규모라 내부망 인프라가 없을 수 있다는 현실적 한계도 언급됐다.

  • 단순 DB 조회면 MCP 서버 대신 쿼리+스키마 정리한 스킬로 충분하다는 의견
  • 여러 팀 서비스 데이터에 직접 접근권한이 없을 때는 OAuth+MCP 조합이 유효하다는 반론
  • 권한은 CRUD 중 Read만 허용해야 하며 admin 키 평문 공유는 위험하다는 경고
  • 내부망+샌드박스 분리 제안이 나왔으나 조직 규모상 인프라 부재 가능성 지적
코딩 AI 모델 비교(솔·오퍼스)?

리셋 주기, Opus 위주 사용 경험, 페이블(Claude Fable) 성능 저하 논란 등 여러 모델 사용 후기가 오감. 서브에이전트를 솔로 여러 개 돌리면 rate limit에 걸려 멈춘다는 경험담이 공유됨. 서브에이전트는 두세 개 정도까지만 병렬로 돌리는 게 안정적이라는 결론으로 모아짐.

  • 8월 1일 새벽 리셋을 앞두고 사용량 상황 공유
  • 그동안 Opus 위주로 쓰다가 다른 모델(솔)로 전환해보는 중
  • 페이블(Claude Fable) 성능 저하 논란이 있었다는 언급
