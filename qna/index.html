클로드를 챗지피티처럼 대화용으로만 쓰던 참가자가 회사 홈페이지 제작과 자산관리 자동화를 위해 클로드코드를 제대로 배우고 싶다고 질문했다. 다른 참가자들은 목적부터 명확히 하고 유튜브로 기초를 익히면서 직접 GPT·클로드에 물어보며 감을 잡으라고 조언했다. 디자인보다 기능 구현에 집중하면 자연스럽게 실력이 는다는 팁도 나왔다. 클로드코드 한국어 입문 가이드 사이트(CC101) 링크도 함께 공유됐다.

  • 질문자는 지금까지 클로드를 챗지피티처럼 대화형 업무보조로만 사용 중
  • 목표는 회사 홈페이지 제작과 회사 자산관리 자동화
  • 조언: 목적을 명확히 하고 유튜브로 기초를 익히며 직접 물어보면서 감을 잡을 것
  • 디자인보다 기능에 초점을 두면 자연스럽게 실력이 는다는 팁
  • cc101.axwith.com(클로드 코드 한국어 입문 가이드) 링크 공유
Orca 멀티 에이전트는 어떻게 쓰는 게 효과적일까요?2번 논의

에이전트끼리 메시지를 주고받으며 협업하는 방식이 실제로 유의미한지 논의했다. 한쪽에서는 컨텍스트 혼탁을 줄이고 모델 간 작업 위임에 쓸 수 있다고 봤지만, 토론형 멀티에이전트는 토큰만 더 쓰고 워크플로우 기반 처리와 결과 차이가 작다는 경험담도 나왔다. 유의미한 활용 사례로는 다른 모델에 이미지 리소스를 요청하거나, 코덱스·클로드·GPT Pro를 교차검증용으로 쓰는 방식이 제시됐다. 봇별 역할과 성격을 다르게 구축하면 판단이 달라질 수 있으므로 용도별 선택이 필요하다는 의견으로 정리됐다.

  • Orca는 복수의 AI 코딩 에이전트를 병렬로 실행·관리하는 도구로 소개됐다.
  • 에이전트별로 독립된 Git 워크트리를 사용한다.
  • 동일 프롬프트를 여러 에이전트에 분산 실행해 결과를 비교·병합할 수 있다.
  • 모바일 앱 알림과 원격 후속 지시 기능이 언급됐다.
  • 설치 방법으로 onOrca.dev, Homebrew, Arch 패키지 명령이 소개됐다.
개발 입문자에게 추천할 만한 IDE가 있을까요?

WSL CLI로 개발한다는 근황 공유와 함께, 입문자에게는 클로드데스크탑 코드가 편할 것 같은데 왜 강의들은 VSCode부터 시작하라고 하는지 질문. VSCode가 무료 기본 IDE라서 그렇다는 답과 함께 Cursor가 바이브코딩 입문용으로 좋다, 안티고니도 입문용으로 쓸만하다는 의견이 나옴. VSCode의 장점으로 폴더·엑셀·DB·이미지 미리보기, 코덱스 연동이 꼽혔고, 파일 변경 이력 확인용으로 git GUI 툴 Fork도 소개됨.

  • WSL CLI 개발 vs 클로드데스크탑 코드 비교 질문
  • VSCode가 무료 기본 IDE라 입문 강의에서 추천된다는 답
  • Cursor는 바이브코딩 입문용으로 좋다는 평가, 안티고니도 입문용으로 쓸만함
  • VSCode 장점: 폴더/엑셀/DB/이미지 미리보기, 코덱스 연동
  • git GUI 툴 Fork로 파일 변경 이력 확인한다는 팁 공유
클로드 코드를 처음 쓰는 사람을 위한 가이드가 있나요?

클로드를 처음 접하는 유저가 무엇부터 시작해야 할지 문의하자, 구독이 필수이며 CS 지식이 있으면 더 수월하다는 답변이 이어졌다. 자연어로만 명령하고 모르는 용어는 쉽게 설명해달라고 요청하는 방식이 실전 팁으로 공유됐다. CS 지식 유무에 따라 대화 턴 수가 달라지므로 조금이라도 공부하면 토큰도 아낄 수 있다는 조언도 나왔다.

  • 클로드 코드는 구독이 있어야 사용 가능하며 데스크탑 앱으로 시작 권장
  • CS 지식이 있으면 클코가 무엇을 하는지 이해가 빨라 편리함
  • 자연어로 아이디어를 설명하고 모르는 용어는 쉽게 설명해달라고 요청하는 방식 공유
  • CS 지식 유무에 따라 대화 턴 수 차이가 나며, 공부하면 토큰도 절약 가능
  • 입문 참고 링크(cc101.axwith.com, github mobius 등) 공유됨
Gemini랑 Claude를 연계해서 쓰는 방법 있나요?

초보 사용자가 Gemini Pro를 Claude와 연계해 쓰는 방법을 물었다. 오픈소스 하네스를 쓰는 방식으로 가재코드와 오모가 제안됐고, 사용 성향을 Claude에게 설명해 적합한 하네스를 추천·설치받는 방법도 언급됐다. 더 쉬운 대안으로 Antigravity Desktop을 설치해 설정을 적용하는 방법이 제시됐다.

  • Gemini Pro와 Claude 연계 방법을 찾는 초보자 질문이 있었다.
  • 가재코드와 오모가 오픈소스 하네스 선택지로 제안됐다.
  • 가재코드는 오픈소스 코딩 에이전트이며 Claude Code류 대안 도구다.
  • 오모는 여러 LLM을 자동 라우팅하고 병렬 실행할 수 있는 멀티 에이전트 코딩 도구다.
  • Antigravity Desktop을 설치해 Gemini 기반 에이전트형 코딩 환경을 쓰는 쉬운 방법도 제안됐다.
VPS에서 클로드코드 작업물을 여러 기기에 동기화하려면 어떻게 하나요?

VPS의 개념과 맥·맥미니·GPU AI 서버와의 용도 차이를 묻는 질문에서 시작해 활용 사례가 폭넓게 공유됐다. VPS에서 개발·배포·오픈소스 서비스 운영, SSH 제어, Claude Code 세션과 함수 도구 운영 등을 할 수 있다는 설명이 나왔다. Syncthing으로 Obsidian과 개발 폴더를 여러 기기에서 실시간에 가깝게 동기화하는 사례도 소개됐다.

  • VPS는 가상 사설 서버라는 용어와 개념이 언급됐다.
  • 개발·배포·오픈소스 서비스 상시 운영 용도로 VPS를 활용하는 사례가 나왔다.
  • SSH를 통한 여러 기기 제어가 가능한 점이 언급됐다.
  • Syncthing으로 Obsidian 및 개발 폴더를 빠르게 동기화하는 사례가 공유됐다.
  • VPS나 미니 홈서버가 있으면 자동화와 CI/CD 활용 폭이 넓어진다는 의견이 나왔다.
VPS를 만능 도구처럼 활용하는 방법에는 어떤 게 있을까요?

VPS 또는 맥에 Claude Code와 라이브러리를 세팅해 두고, 요청을 보내면 라우팅해 기능을 수행하는 개인용 백엔드·만능앱 형태의 활용법이 소개됐다. 모바일에서 영상 다운로드 같은 작업을 처리하는 예시가 언급됐고, 이를 따라 개인 세팅을 해보겠다는 반응이 나왔다.

  • Claude Code 세션을 서버 측처럼 활용하는 방식이 언급됐다.
  • 필요한 함수 도구와 라이브러리를 미리 설치해 둔다는 구상이다.
  • 요청을 라우팅해 자동으로 기능을 수행하는 개인 도구 형태가 소개됐다.
  • 영상 다운로드 같은 모바일 연계 작업이 예시로 나왔다.
  • 개인 환경에도 유사한 세팅을 적용해 보겠다는 반응이 나왔다.
AI가 예스맨처럼 무조건 동조하는 문제는 어떻게 해결하나요?

코덱스로 만든 프로그램이 마음에 안 들어 클로드로 옮기면 나아질지 질문이 올라왔다. 원인은 모델 자체보다 기획 부족으로, 불확실한 정보를 AI가 임의로 정해버리는 데 있다는 지적이 나왔다. 기획 단계에서 불확실한 부분을 충분히 정의하고 시작하라는 조언과, '왜?'를 계속 물어보라는 팁이 제시됐다.

  • 초보 개발자가 AI의 동조(예스맨) 성향 때문에 방향이 흐트러진다고 호소
  • 원인은 모델 문제가 아니라 기획 부족이라는 진단
  • 불확실한 정보를 사전에 충분히 정의하고 시작할 것을 권장
  • AI에게 'why'를 계속 물어보라는 실용 팁 제시
Claude Code를 설치할 때 Git은 어떻게 설정하나요?

Claude Code 사용을 위해 터미널 설치가 첫 단계인지 질문이 나왔다. 맥북에서 Git 설치가 되지 않는 문제를 기기 등급 탓으로 오해하는 대화가 이어졌다. 해결 방향으로 터미널에서 Xcode 명령줄 도구를 설치하면 된다는 안내가 나왔다.

  • Claude Code 시작 시 터미널 사용 여부가 질문됐다.
  • 맥북에서 Git이 설치되지 않는 문제를 호소했다.
  • 기기 가격이나 모델보다 개발 도구 설치 문제로 보는 흐름이었다.
  • Xcode Command Line Tools 설치가 해결 방향으로 제시됐다.
AI로 업무팀을 병렬 운영하려면 어떻게 해야 하나요?

Visual Studio에서 Claude Code로 AI 비서에게 업무를 맡기고, 부서처럼 역할을 나눈 여러 팀을 병렬 운영하는 방법을 문의했다. 인스타그램에서 보이는 자동화 업무 팀과 같은 형태를 구현하고 싶다는 목적이 제시됐다. 역할 분담형 멀티에이전트 자동화 구성에 대한 초기 세팅 질문이다.

  • Visual Studio와 Claude Code 조합이 전제됐다.
  • AI 비서에게 업무를 위임하는 방식이 목표였다.
  • 여러 에이전트를 부서처럼 역할 분담시키려는 구상이었다.
  • 병렬 운영과 업무 자동화의 대략적 세팅을 요청했다.
클로드에서 GPT 이미지 생성 기능을 쓸 수 있나요?

클로드가 GPT를 통해 이미지를 생성하도록 만들 수 있는지 질문이 나왔다. API를 직접 쓰는 방식 외에 품앗이라는 도구를 통해 이미지 생성을 요청할 수 있다는 정보가 공유됐다. 채팅에서도 사용 가능한지 묻는 질문에 사용법 예시와 저장소 링크가 제시됐고, 질문자는 해결책을 찾았다며 호응했다.

  • 클로드가 외부 이미지 생성 모델을 호출하는 방식에 대한 질문이 나왔다.
  • 직접 API 연동 대신 품앗이 도구가 대안으로 제시됐다.
  • 이미지 생성 요청용 슬래시 명령 예시가 공유됐다.
  • 도구 사용 전 요구사항을 먼저 질문해 정보를 얻는 흐름도 언급됐다.
코워크에서 코드로 전환하려면 어떻게 하나요?

코워크에 쌓인 프로젝트 기록과 자료를 Claude Code로 옮겨 AI 직원 자동화를 이어갈 방법이 논의됐다. 코드 쪽에서 현재와 같은 방식으로 대화를 시작하고, 기존 맥락이나 자료를 가져오도록 요청하면 된다는 조언이 나왔다. 데스크톱 앱에서도 코드 작업이 가능하며, 터미널과 원리는 크게 다르지 않다는 설명이 덧붙었다.

  • AI 직원형 자동화는 코워크보다 Claude Code가 더 적합하다는 의견이 나왔다.
  • 기존 코워크 대화와 프로젝트 맥락은 코드 쪽으로 가져오도록 요청할 수 있다고 안내됐다.
  • 목적을 먼저 설명하고 모르는 부분을 솔직히 밝히며 대화를 시작하라는 팁이 제시됐다.
  • 데스크톱 앱에서도 코드 작업을 진행할 수 있다고 설명됐다.
사칭 계정이 보낸 링크는 어떻게 조심해야 하나요?

커뮤니티 관련 사칭 계정이 늘었다는 이야기가 나왔고, 사칭의 목적은 주식 리딩방 유도·가입자 확보 등일 수 있다는 의견이 제기됐다. 이어 외부 링크를 Claude에 확인시키려다 데스크톱 앱이 종료되고 재설치를 요구한 사례가 공유됐다. 브라우저 도구의 헤드리스 브라우저 서버 재시도와 프로세스 누적, 메모리 부족이 원인일 가능성이 언급됐으며, 링크를 열거나 전달하기 전 위험성을 점검하고 검증하는 습관이 강조됐다.

  • 사칭 계정이 주식 리딩방 등으로 유도할 수 있다는 추정이 나왔다.
  • 외부 링크 처리 중 Claude 데스크톱 앱이 종료되고 재설치를 요구한 사례가 있었다.
  • 헤드리스 브라우저 서버의 반복 실패와 백그라운드 프로세스 누적 가능성이 설명됐다.
  • 링크의 위험성을 먼저 확인하고 결과를 검증하는 습관이 필요하다는 의견이 나왔다.
데스크탑 컨트롤의 cowork 탭 위치를 바꿀 수 있나요?

새로 설치한 클로드 코드에서 데스크탑 전체를 컨트롤하던 기능이 사라졌다는 문의가 있었다. 답변으로 cowork 탭이 채팅창 아래로 위치가 옮겨졌다는 설명과, 업데이트를 오래 안 했거나 Hyper-V가 꺼져 있으면 안 보일 수 있다는 안내가 나왔다.

오퍼스 5로 바뀐 뒤 하네스 동작이 예전보다 멍청해졌다는 불만이 나옴 — 시도·재시도 없이 그냥 넘어가거나 배포와 테스트 순서가 꼬인다는 사례가 공유됨. 200 Max 요금제가 100 Max 대비 광고된 4배보다 실제 체감 차이는 2~3배 정도라는 의견이 다수 나옴. 대응으로 모델별 오케스트레이션 구조를 만들어 테스트 중이라는 공유가 있었고, 순정 하네스가 이전 커스텀 하네스보다 낫다는 의견도 나옴. 4배라는 수치는 5시간 세션에만 적용되고 주간 한도엔 해당 안 될 수 있다는 추가 정보도 나옴.

  • 오퍼스 5 이후 하네스가 시도·재시도 없이 그냥 진행한다는 불만
  • 200max vs 100max 실사용 차이는 광고된 4배가 아니라 2~3배 체감
  • 대응책으로 모델별 오케스트레이션 구조 테스트 중
  • 이전 커스텀 하네스보다 순정이 낫다는 의견
  • 4배 수치는 5시간 세션 한정이고 주간 한도엔 미적용 가능성 언급
chatmux 개발은 지금 어디까지 진행됐나요?

chatmux 저장소가 공유됐지만 당시 정비와 리뷰 작업 중이라 접근 문제가 언급됐다. 개발자는 유즈케이스를 더 쌓아야 한다고 했고, 문제 제보를 받겠다고 밝혔다. Rust로 만든 이유로 속도와 메모리 사용량이 거론됐다.

  • 저장소 접근 문제는 리뷰 및 수정 작업 과정과 연결돼 언급됐다.
  • 향후 유즈케이스를 더 축적할 필요가 있다고 했다.
  • Rust를 선택한 이유로 빠른 반응성과 낮은 메모리 사용량을 들었다.
  • 개발자가 직접 문제 제보를 받겠다는 의사를 밝혔다.
헤르메스 에이전트는 실제로 어떻게 활용하나요?

헤르메스 에이전트의 패치 소식과 실제 사용 경험을 이야기했다. 로컬 모델에 연결하면 다소 성능이 떨어질 수 있으나, 결과물의 문제를 구체적 사실 기반으로 지적하며 반복 지시하면 개선된다는 경험담이 나왔다. Claude 구독을 직접 연결하는 방식은 정지 위험이 있을 수 있다는 우려가 제기됐고, 비용 없이 로컬 모델을 연결해 간단한 용도로 쓰는 데는 만족한다는 의견이 있었다.

  • 헤르메스 에이전트는 Nous Research의 오픈소스 자기학습형 AI 에이전트로 소개됐다.
  • 향후 패치에 맞춰 설치 구성을 다시 정비할 계획이 언급됐다.
  • 결과물 오류를 팩트 기반으로 지적하며 재작업을 요구하는 사용법이 공유됐다.
  • Claude 구독 인증 활용은 제재 가능성을 우려하는 의견이 나왔다.
  • 로컬 모델 연결은 비용 절감용 간단한 작업에 적합하다는 평가가 있었다.
Spark와 헤르메스는 함께 어떻게 활용할 수 있나요?

Nimotron으로 속도를 내고 Spark를 개인용으로 사용한다는 대화가 오감. 약 45~50 토큰 수준이면 Hermes 용도로 쓸 만하다는 평가가 언급됨. 이후 Spark에서 어떤 모델로 서빙하는지 질문이 나왔지만 답은 기록되지 않음.

  • Spark를 개인용으로 사용한다는 언급이 있음.
  • GitHub Spark는 자연어 설명으로 풀스택 웹앱을 만드는 AI 앱 빌더로 확인됨.
  • Hermes Agent는 도구 실행·메모리·MCP 기반 Claude Code 연동을 지원하는 오픈소스 에이전트 플랫폼으로 확인됨.
  • 속도 지표가 약 45~50이면 Hermes 활용에 만족할 만하다는 의견이 나옴.
  • Spark의 서빙 모델에 대한 질문이 제기됨.
긴 작업할 때 세션이나 컨텍스트는 어떻게 관리하세요?

긴 세션에서 컨텍스트가 소진되고 compact를 반복하면 작업 맥락과 CLAUDE.md 내용이 유실될 수 있다는 문제를 다뤘다. compact와 /CLEAR를 모두 지양하고, 토큰 사용 임계치 전에 세션을 강제로 정리해 메모리를 기록하는 방안이 제안됐다. 한 기능을 반드시 하나의 세션에서 끝내야 한다는 전제를 버리고, 작업 단위와 핸드오프를 설계해야 한다는 조언이 나왔다.

  • 대규모 솔루션을 바이브 코딩으로 구현하면서 메인 세션의 맥락 붕괴 문제가 제기됐다.
  • 마스터맵 문서를 갱신해 참고시키는 방식이 사용 중이었으나, 상시 읽기는 컨텍스트 윈도우를 크게 소모할 수 있다는 의견이 나왔다.
  • 컨텍스트 50% 수준마다 compact하는 방식은 좋은 해결책이 아니라는 문제의식이 공유됐다.
  • 토큰 한도를 약 90%로 두고 85%에서 세션 정리와 메모리 기록을 강제하는 방식이 제안됐다.
  • 한 기능을 하나의 긴 세션에서 완성할 필요가 있는지 재검토해야 한다는 질문이 제기됐다.
플러그인을 쓰면 토큰이 얼마나 더 소비되나요?

플러그인이 MCP처럼 실제 호출 시점에만 지연 로딩되어 토큰을 쓰는지 질문이 나왔다. 구현마다 로드·노출 시점이 달라 일괄적으로 답할 수 없고, 과거에는 미리 호출돼 컨텍스트를 크게 소비한 경우도 있었다는 의견이 나왔다. 플러그인은 스킬·훅·MCP를 묶은 형태로 보이며, 훅의 pre/post 스크립트가 컨텍스트를 소비할 수 있다는 설명이 덧붙었다.

  • 플러그인 도구 스키마의 지연 로딩과 토큰 소비 시점이 질문됐다.
  • 로드·노출 시점은 플러그인 구현 설계마다 다르다는 의견이 제시됐다.
  • 사전 호출 방식은 컨텍스트 윈도우를 많이 소모할 수 있다는 경험담이 나왔다.
  • pre/post 훅 스크립트가 컨텍스트 사용량에 영향을 줄 수 있다는 설명이 나왔다.
  • 플러그인 호출 뒤 내부 도구 호출 여부를 판단하는 구조라는 견해가 제시됐다.
헤드룸에서 토큰을 압축하는 방법이 있나요?

Claude Code 컨텍스트를 아끼는 headroom-ai 글과 GitHub 저장소가 공유됐다. headroom-ai는 도구 출력, 로그, RAG 청크 등을 LLM 전달 전 압축해 토큰 사용량을 줄이는 오픈소스 도구로 소개됐다. 영어로 대화해 토큰을 아끼던 방식 대신 headroom을 쓰면 한국어 사용 부담을 줄일 수 있다는 경험담이 나왔다. Claude 실행 래핑 시 권한 우회 옵션을 넣는 법과 Codex Desktop에서의 적용 방법도 질문됐지만 답변은 기록되지 않았다.

  • headroom-ai는 도구 출력·로그·RAG 청크 등을 압축해 토큰 사용량을 줄이는 도구다.
  • 라이브러리·프록시·MCP 서버 형태로 Claude Code 등과 연동할 수 있다.
  • 토큰 절약을 위해 영어로 대화하던 습관을 줄일 수 있다는 사용 경험이 공유됐다.
  • Claude 래핑 실행 시 권한 관련 옵션 전달법이 질문됐다.
  • Codex Desktop에서 headroom을 적용하는 방법도 질문됐다.
Cursor랑 Grok 요금 한도는 어떻게 다른가요?

Cursor Ultra와 Grok 구독의 사용량 한도가 각각 분리되는지 논의됐고, 각각 별도라는 답변이 나왔다. Cursor에서 Fable·Grok·Composer 등 모델을 어떻게 배분해 쓸지 의견이 오갔다. Cursor에 클로드 모델이 있다는 설명이 있었지만, Claude Code를 Cursor에서 직접 돌린다는 뜻은 아니라고 정리됐다.

  • Cursor Ultra 토큰과 Grok Heavy 토큰은 별도 한도라는 답변이 나왔다.
  • Fable을 Cursor에서 쓰면 사용량이 빠르게 소진될 수 있다는 의견이 있었다.
  • Grok과 Composer를 우선 활용하고 남는 한도로 Fable을 쓰자는 제안이 나왔다.
  • Grok이 Composer보다 낫다고 느끼는 사용자 의견도 있었다.
  • Cursor는 Claude 모델을 제공하지만 Claude Code 실행과는 구분된다고 설명됐다.
그록봇 서비스 써본 사람 후기 있나요?

그록봇 사용 경험과 구독 가치에 대한 질문이 나왔다. 서비스는 컴퓨터 한 대에 Grok 4.6을 붙여 주고, 여러 에이전트가 해당 환경을 공유하는 개념으로 설명됐다. 커서나 그록 요금제까지 함께 활용하려는 경우에는 가치가 있을 수 있지만, 클로드와 클로드 코드 조합에 만족한다면 굳이 옮길 필요는 없다는 의견이 제시됐다. 이미지와 동영상 생성도 가능하다는 경험담이 덧붙었다.

  • 그록봇은 컴퓨터 한 대와 Grok 4.6을 결합한 서비스로 설명됐다.
  • 여러 에이전트를 소환하고 메시지를 주고받게 하는 구성이 언급됐다.
  • 커서 또는 그록 요금제를 함께 쓸 사용자에게 가치가 있을 수 있다는 의견이 나왔다.
  • 클로드 코드 중심 사용자에게는 이전 필요성이 낮다는 평가가 있었다.
  • 이미지 및 동영상 생성 가능 경험담이 공유됐다.
그록이랑 다른 도구들 관련 질문은 어디서 모아보나요?

Thinking Machine의 방향성, 그록봇으로 클로드 코드에서 넘어갈 가치, 오픈코덱스와 오픈코드의 차이 등 여러 도구 관련 질문이 이어졌다. SOL 1M 변경 경험과 aside 사용 경험을 묻는 질문도 나왔다. 그록과 GLM의 토큰 생성 속도 비교 질문도 있었지만 이 구간에서는 답변이 제시되지 않았다.

  • Thinking Machine이 추구하는 방향에 대한 질문이 있었다.
  • 그록봇과 클로드 코드 사이의 이전 가치가 질문됐다.
  • 오픈코덱스와 오픈코드의 차이를 묻는 질문이 나왔다.
  • SOL 1M 변경 경험 및 aside 사용 경험을 찾는 요청이 있었다.
  • 그록과 GLM의 토큰 속도 비교 질문은 답변 없이 남았다.
Claude 엔터프라이즈 써보신 분 경험 어떤가요?

Claude 엔터프라이즈 요금제에서 1M 컨텍스트를 기대했던 경험과 실제 제약이 공유됐다. 당시 API에서는 1M 컨텍스트가 가능했으나 Claude Code에서는 지원되지 않아 기대와 달랐다는 사례가 나왔다. 연간 구독 비용이 한 번에 청구됐고, API 사용료가 하루 약 50만 원 수준까지 나왔다는 경험도 언급됐다. 이후 Opus 1M 출시로 더 나은 선택지를 찾았다는 반응이 있었다.

  • 엔터프라이즈 요금제로 1M 컨텍스트를 기대하고 신청했던 사례가 공유됐다.
  • 실제 Claude Code에서는 해당 기능을 사용할 수 없었다는 불만이 나왔다.
  • 연간 구독 비용이 약 2만6천 달러로 한 번에 청구된 사례가 언급됐다.
  • 당시 1M 컨텍스트는 API에서만 가능했다는 설명이 나왔다.
  • Opus 1M 등장 후 비용과 활용 면에서 개선됐다는 평가가 있었다.
클로드 요금제별로 쓸 수 있는 모델이 어떻게 다른가요?

대규모 자동화를 바이브 코딩으로 구성하려면 월 20달러 기본 요금제는 제한이 크고 최소 100달러급 요금제가 현실적이라는 의견이 나왔다. 초기 구성과 시행착오 과정에서 토큰 사용량이 많이 들 수 있다는 설명이 뒤따랐다. 모델은 오푸스보다 소넷을 우선 쓰라는 조언이 있었고, 오푸스는 빠르게 제한에 걸릴 수 있다는 경험담이 공유됐다.

  • AI 직원 자동화 규모는 작지 않아 초기 구현에 많은 사용량이 들 수 있다는 의견이 나왔다.
  • 월 20달러 요금제는 체험 수준으로 평가됐다.
  • 실질적인 작업을 하려면 최소 100달러급 요금제를 권하는 의견이 나왔다.
  • 오푸스는 사용 제한이 빨리 올 수 있어 소넷을 우선 쓰라는 조언이 있었다.
  • 메인 대화 모델은 사용자가 매번 바꾸고, 내부 서브에이전트 모델은 상황에 따라 지정할 수 있다는 설명이 나왔다.
모바일 환경에서 VPS로 작업하려면 어떻게 설정해야 하나요?

모바일 중심으로 Claude Code와 Codex를 쓰고 GitHub Actions로 자동화하는 사용자가 로컬 데스크톱, VPS, 에이전트 도구의 선택 기준을 질문했다. 응답에서는 Hermes는 키 관리 부담이 크고, 24시간 구동 서버가 필요해지는 시점에는 VPS로 먼저 경험한 뒤 미니 PC 서버로 확장하는 경로가 제안됐다. 저가 VPS를 활용해 Hermes를 운영하고 텔레그램·크론잡 기반으로 결과를 받는 경험담도 공유됐다. 다만 타 리전 VPS에서 브라우저 로그인과 여러 서비스 접근을 할 경우 경고 또는 계정 제한 가능성을 우려하는 질문이 제기됐고, 개인 사용량 집계와 세션 아카이빙 같은 관리 시스템 때문에 Cowork를 피하는 이유도 설명됐다.

  • 모바일 우선 환경에서 Claude Code 앱, Codex 원격 작업, GitHub Actions 자동화를 병행하는 사례가 공유됐다.

계획은 오푸스로, 코드 작성은 소넷으로 나눠 써도 되는지 묻는 질문에서 심도 있는 논의가 이어졌다. 짧은 작업은 모델을 나누면 오히려 토큰 손해이고, 30분~1시간 걸리는 장기 플랜이나 프론트/백엔드 분리 같은 경우에 나누는 게 효율적이라는 의견이 나왔다. 명확한 지시서가 있는 단순 작업은 소넷이 낫고, 오푸스는 상황에 따라 하위 에이전트를 안 쓰고 혼자 다 처리해버리는 경우도 있다는 관찰이 공유됐다. 개인 메모리·skills 설정 여부에 따라 결과 차이가 크다는 데로 결론이 모였다.

  • 오푸스가 상황에 따라 하위 에이전트 없이 혼자 다 처리하는 경우도 있음
  • 개인 메모리·skills 설정 여부에 따라 결과 편차가 크다는 결론

윤문 플러그인과 insane-writer 중 뭐가 더 나은가요?

  • 실측 상 yunmun 0.5.0 재작성 경로가 특정 원고에서 완주 실패하는 버그 발견
  • 실제 비교에서 원문 표현이 더 나은 경우도 많아 윤문의 필요성에 의문 제기

  • API와 구독형 환경에 따라 컨텍스트 길이가 다를 수 있다는 의견이 제시됐다.
코덱스 리셋하면 모델이 어떻게 바뀌나요?

코덱스 리셋으로 작업 두 개를 잃었다는 아쉬움이 나왔고, 사용량 초기화 시점도 추정됐다. 한 참여자는 최근 Claude보다 Codex를 더 자주 쓴다고 했다. 문서 작업에서는 솔을 Work 모드로 사용했을 때 PPT를 잘 만들어준다는 경험도 공유됐으며, OpenRouter 사용 제안도 나왔다.

  • 코덱스 리셋으로 작업이 손실됐다는 경험이 공유됐다.
  • 초기화 시점이 오전 11시 무렵일 수 있다는 추정이 나왔다.
  • 최근 Claude보다 Codex 사용 빈도가 높다는 의견이 있었다.
  • 솔의 Work 모드가 문서 작업과 PPT 생성에 유용했다는 후기가 나왔다.
  • 여러 모델 접근 경로로 OpenRouter 사용 제안이 있었다.
Qwen3.8-27B 써보신 분 반응이 어떤가요?

Qwen3.8-27B 관련 글이 공유된 뒤 3.8 계열의 툴콜링 개선과 실제 구동 성능에 대한 평가가 이어졌다. 툴·스킬을 가져오는 능력과 작업 완결성은 3.6보다 개선됐다는 체감이 나왔지만, 벤치마크만 믿기보다 직접 사용해 보는 것이 낫다는 의견도 제시됐다. Opus라는 표현은 로컬 Opus 모델을 뜻하는 것이 아니라 성능 수준을 비유한 것이라는 설명이 나왔다.

  • Qwen3.8-27B 관련 매거진 글이 공유됐다.
  • 3.8에서 툴콜링 및 도구·스킬 호출 능력이 개선됐다는 체감이 언급됐다.
  • DGX Spark에서는 속도가 느리지만 참고 사용할 수 있는 수준이라는 평가가 나왔다.
  • 벤치마크 점수는 학습 최적화에 영향을 받을 수 있으므로 실사용 검증이 중요하다는 의견이 나왔다.
  • 로컬 모델 논의에서의 Opus 표기는 실제 로컬 Opus 배포판이 아니라 성능 비유라고 설명됐다.
오픈코덱스 계정을 쓰면 어떤 리스크가 있나요?

VS Code의 Claude Code 환경에 GPT나 DeepSeek 등 다른 회사 LLM을 연결할 수 있는지 질문이 나왔다. 한 CLI에서 여러 회사 모델을 쓰는 도구로 OpenCodex가 거론됐다. OpenCodex로 Claude를 쓰다가 계정 제재를 받은 사례가 있는지, 과거 OpenClaw 관련 제재 소문과 연결해 우려하는 질문도 나왔지만 결론은 제시되지 않았다.

  • VS Code와 Claude Code에서 타사 LLM 연결 가능 여부가 질문됐다.
  • 여러 모델을 한 CLI에서 쓰는 도구로 OpenCodex가 언급됐다.
  • OpenCodex는 여러 AI 모델을 Codex·Claude Code와 연결하는 오픈소스 로컬 프록시 도구다.
  • 계정 정지·제재 위험에 대한 우려가 제기됐지만 확인된 사례나 결론은 대화에 없다.
  • OpenClaw는 메신저 등을 통해 자동화 작업을 지시하는 self-hosted AI 에이전트·게이트웨이 도구로 언급됐다.
멀티 모델로 역할을 어떻게 나눠서 쓰나요?

프로젝트 빌드에서 Claude 기반 구성, Fable 운영, Opus·Sonnet 구현, GPT 계열 최종 감사처럼 모델별 역할을 나누는 워크플로우가 제안됐다. 이를 실행할 CLI 선택이 질문됐고, Claude Code와 Codex를 연동해 서로 협업시키는 방법도 이어서 논의됐다. 두 도구가 자동으로 대화하는 것이 아니라 공유 규칙과 전달 절차를 갖춘 하네스가 필요하다는 설명이 나왔다. 같은 폴더의 파일을 순차적으로 운영하고 역할·인계 규칙을 따로 정해야 한다는 방향이 제시됐다.

  • 모델별로 운영·구현·감사 역할을 분리하는 프로젝트 구성안이 제시됐다.
  • Fable은 Anthropic의 최고 등급 Claude 모델로 장시간 자율 작업과 복잡한 코딩·에이전트 작업에 특화된 것으로 언급됐다.
  • Claude Code와 Codex의 연동 가능 여부가 질문됐다.
  • 자동 대화보다 공유 규칙과 전달 절차를 갖춘 하네스가 필요하다는 설명이 나왔다.
  • 같은 프로젝트 폴더의 파일을 순차적으로 다루고 역할·인계 규칙을 별도로 설계해야 한다는 흐름이었다.
Fable이랑 GPT 모델은 성능 차이가 얼마나 나나요?

GPT Pro 모델, Fable, 그록, GPT Terra의 체감 성능과 사용처를 비교했다. Fable은 장문 컨텍스트와 복잡한 코딩·에이전트 작업에서 높은 평가를 받았고, 사용량 한도가 빨리 소진된다는 경험도 나왔다. 그록은 GPT Terra보다 조금 빠르지만 다소 덜 똑똑하다는 체감 비교가 제시됐으며, 그록 4.6이 Claude Opus 급일 것이라는 기대에는 부정적 반응이 나왔다. 일부 이용자는 Sol 또는 Opus급 이하 모델은 잘 사용하지 않는다고 밝혔다.

  • Fable은 장시간 자율 작업과 복잡한 코딩·에이전트 작업에 특화된 상위 Claude 모델로 언급됐다.
  • Fable의 1M 컨텍스트와 성능이 특히 높게 평가됐다.
  • 일부 사용자는 Fable을 하루 만에 주간 사용량의 상당 부분 소진할 만큼 많이 사용했다고 말했다.
  • 그록은 속도 측면의 장점이 있지만 최상위 추론·코딩 모델과 동급으로 보기는 어렵다는 의견이 나왔다.
  • 그록의 강점으로 이미지·영상 생성과 실시간 이슈 대응이 언급됐다.
Fable 브릿지는 어떻게 활용하면 좋을까요?

Fable을 웹에서만 쓰는 현재 제약과 Claude Code 등에 연결하는 브릿지 활용 가능성이 논의됐다. 브릿지를 만들어 연결해 볼 계획이 언급됐지만, 브릿지 방식은 사용성이 불편해 웹 전용으로 보는 편이 낫다는 의견도 있었다. Codex에 들어오면 작업용으로 활용하고 싶다는 수요가 나왔고, 커서에서 Fable을 쓸 수 있다는 점이 구독 가치 논의와 연결됐다.

  • Fable은 당시 웹 중심 사용으로 인식됐다.
  • Claude Code에 연결하기 위한 브릿지 제작 계획이 언급됐다.
  • 브릿지로 연결하면 기능은 가능해도 사용성이 불편할 수 있다는 경험적 의견이 있었다.
  • Codex 같은 작업 환경에 통합되기를 바라는 수요가 나왔다.
  • 커서에서 Fable 사용 가능 여부가 구독 선택의 주요 요소로 거론됐다.
Halo 성능은 실제로 어느 정도일까?

AMD가 과기부에 기증했다는 Halo의 정체와 성능이 화제가 됐다. Halo는 Claude Code·Codex 등 여러 AI 엔진을 연결해 쓰는 데스크톱 AI 워크스테이션 도구로 언급됐다. 프론티어 상용 모델과는 성격이 다르며, 로컬 Qwen 계열 구동 가능성과 속도 사례가 논의됐다. Qwen3.8 27B에서 리즈닝을 끄면 32 tok/s 사례가 있다는 말이 나왔고, 200B급 구동은 현실적이지 않다는 반응이 있었다.

  • Halo는 여러 AI 엔진을 붙여 쓰는 데스크톱 AI 워크스테이션 도구로 소개됐다.
  • 프론티어 상용 모델과 동일선상 비교보다는 로컬 모델 운용 관점에서 봐야 한다는 의견이 나왔다.
  • Qwen3.8 27B를 리즈닝 없이 32 tok/s로 돌린 사례가 언급됐다.
  • 200B급 모델 구동에는 회의적인 반응이 나왔다.
  • 발열과 전력 부담도 농담 섞여 언급됐다.
Mythos 5 보안 스캔은 어떻게 진행하나요?

Claude Enterprise에서 Mythos 5 기반 보안 스캔을 공개 베타로 제공한다는 소식이 공유됐다. GitHub 저장소를 지정하면 취약점, CWE, 심각도, 수정안을 제시하고 패치는 웹 Claude Code에서 열 수 있다고 소개됐다. 별도 모델 권한을 받지 않아도 된다는 설명도 포함됐다.

  • Claude Enterprise의 Mythos 5 보안 스캔 공개 베타가 언급됐다.
  • 코드베이스 보안 점검에 고성능 모델을 활용하는 기능이다.
  • GitHub 저장소를 대상으로 취약점을 탐지할 수 있다.
  • CWE, 심각도, 수정안까지 제공한다고 소개됐다.
  • 패치를 웹 Claude Code에서 열 수 있다고 언급됐다.
OpenRouter와 OpenCode는 실제로 어떤 점이 다른가요?

OpenRouter 무료 사용을 위해 10달러 충전이 필요한지 질문이 나왔다. 이어 초보자부터 전문가 수준까지 이해할 수 있게 OpenRouter를 설명해 달라는 요청과 함께 OpenCode, OpenCodex의 차이를 묻는 질문이 제기됐다. OpenCode는 여러 AI 모델을 연결하는 터미널 기반 오픈소스 코딩 에이전트이며, OpenCodex는 Codex·Claude Code 등에 다수 LLM 제공자를 연결하는 로컬 프록시 도구로 구분된다.

  • OpenRouter 무료 사용을 위해 선충전이 필요한지 질문이 나왔다.
  • OpenRouter를 초보자 관점부터 전문 수준까지 설명해 달라는 요청이 있었다.
  • OpenCode는 여러 AI 모델을 연결해 쓰는 터미널 기반 오픈소스 AI 코딩 에이전트다.
  • OpenCodex는 Codex CLI·App·SDK와 Claude Code에 다수 LLM 제공자를 연결하는 로컬 프록시 도구다.
  • 세 서비스·도구의 역할 차이를 명확히 비교하려는 수요가 확인됐다.
코딩용으로는 솔이랑 오퍼스 중 어떤 모델이 나을까요?

리셋 주기, Opus 위주 사용 경험, 페이블(Claude Fable) 성능 저하 논란 등 여러 모델 사용 후기가 오감. 서브에이전트를 솔로 여러 개 돌리면 rate limit에 걸려 멈춘다는 경험담이 공유됨. 서브에이전트는 두세 개 정도까지만 병렬로 돌리는 게 안정적이라는 결론으로 모아짐.

  • 8월 1일 새벽 리셋을 앞두고 사용량 상황 공유
  • 그동안 Opus 위주로 쓰다가 다른 모델(솔)로 전환해보는 중
  • 페이블(Claude Fable) 성능 저하 논란이 있었다는 언급
  • 서브에이전트를 다수 병렬 실행하면 rate limit로 실패, 2~3개가 적정선
챗봇용으로는 어떤 LLM 모델을 골라야 할까요?

챗봇 개발 시 비용 절감을 위해 레포분석 같은 무거운 작업은 소넷, 나머지 잡무는 하이쿠로 나눠쓴다는 얘기로 시작. GPT-5.4, 제미니 플래시, 딥시크 등 다양한 모델의 가성비를 비교했고, Qwen을 로컬(맥스튜디오)로 돌리면 동시 요청 시 매우 느려진다는 실측 경험이 공유됨. 결국 컨텍스트 크기와 챗봇 목적에 따라 맞는 모델이 다르므로 여러 개 써보고 고르는 게 낫다는 결론.

  • 소넷은 레포분석 등 무거운 작업, 하이쿠는 잡담·경량 작업에 배분해 비용 절감
  • Qwen을 로컬 맥스튜디오로 돌리면 동시 요청 시 초당 10토큰도 안 나올 정도로 느림
  • 딥시크는 저렴하고 성능도 괜찮아 엑셀 정리 같은 간단한 용도엔 충분
  • 비동기+로그불필요 작업은 클로드코드에 물리고, 실시간 필요시엔 GPT API를 추천
역할을 나눠서 에이전트 구성한 사례 있으신가요?

클로드코드와 코덱스를 역할별로 나눠 사용하는 구성이 공유됨. 클코는 총괄(2개)/자료조사/개인스케줄/카톡요약 및 위키자동화/글쓰기를 담당하고, 코덱스는 총괄+자료조사/이미지생성을 담당. 향후 보안 관련 역할도 추가할 예정이라고 언급됨.

  • 클로드코드와 코덱스를 역할별로 분담해서 운영
  • 클코 담당: 총괄 2개, 자료조사, 개인스케줄, 카톡 요약·위키 자동화, 글쓰기
  • 코덱스 담당: 총괄+자료조사, 이미지생성
  • 추후 보안 관련 역할 추가 예정
회의록 화자분리해서 전사하는 방법 있을까요?

다른 녹음 장비로 녹음한 걸 무료로 클로드코드 이용해서 회의록 요약할 수 있는지 질문. 클코 자체 사용은 무료가 아니고, 화자분리까지 하려면 유료 API가 필요하다는 답변. 맥이면 애플 자체 위스퍼/Speech to Text로 무료 전사 후 클코로 처리하는 방법도 소개됨. 화자분리 지원 로컬 모델도 있지만 API보다 정확도는 낮다는 의견도 나옴.

  • 클로드코드 자체 사용은 무료가 아님
  • 화자분리까지 하려면 유료 API 필요
  • 맥에서는 애플 Speech to Text/위스퍼로 무료 전사 후 클코 처리 가능
  • 화자분리 지원 로컬 모델도 있으나 정확도는 API보다 낮음
하네스 설계할 때 Fable5랑 Opus5 중 뭐가 나을까요?

클로드 코드로 프로젝트 시작 시 하네스(작업 구조) 설계를 먼저 해야 하는지 질문이 나옴. 이어서 Fable5와 Opus5의 특징 차이, 어느 걸 메인으로 써야 할지, 메인을 Opus5로 쓸 경우 Fable5는 어떤 용도로 병행하면 좋을지에 대한 질문이 이어짐. Codex·Claude 최신 모델이 하네스 개념 자체를 인지하고 있는지, 어중간한 하네스보다 자유도를 높여주는 게 더 나은 결과를 낼 수 있는지도 질문됨.

  • 프로젝트 초기 하네스 설계 필요성에 대한 질문

요즘 보편적으로 쓰기 좋은 검색 API를 묻는 질문이 나왔고 인세인 서치가 추천 후보로 언급됐다. 인세인 서치는 Claude Code용 플러그인으로, 에이전트 접근이 막힌 공개 웹페이지를 여러 우회 방식을 단계적으로 시도해 읽어오는 검색·크롤링 도구다.

  • Claude 외 보조 AI 선택에 관한 질문이었다.
  • ChatGPT가 추천됐다.
  • 모델별 장단점이나 용도별 비교는 논의되지 않았다.
  • 검색 API 선택 질문이 제기됐다.
  • 인세인 서치가 추천 도구로 언급됐다.
클로드 일부 서버에 장애가 있는 건가요?2번 논의

새벽 시간대에 클로드가 응답하지 않는 장애가 발생, 여러 명이 동시에 겪음. CNET 기사로 지피티에 이은 광범위한 장애 소식이 공유됨. 아침 8시경에는 대체로 복구된 것으로 확인됨.

  • 새벽 시간대 클로드 응답 불가 다수 보고
  • CNET 기사로 광범위 장애 소식 공유
  • 아침 8시경 복구 확인
  • 클로드 응답이 갑자기 멈추는 현상 보고
  • 일부 서버 장애로 추정, 다른 계정/세션으로 전환하니 정상 작동
클로드 세션을 외부 메신저나 앱과 연동할 수 있나요?

클로드 세션을 모바일 앱 밖의 별도 창이나 다른 메신저(텔레그램, 디스코드, 슬랙, iMessage)에서 조작할 수 있는지 질문이 나왔다. Channels가 공식 지원 기능이며, 직접 커스텀 앱을 만들려면 SDK나 headless 모드가 정석이라는 답이 왔다. 실제로 슬랙과 디스코드 TUI에 연동해 쓰고 있다는 사례들이 공유됐고, Antigravity의 sidecar 문서와 agentapi 명령어 예시 링크도 함께 올라왔다.

  • Channels는 클로드코드 공식 지원 기능으로 텔레그램/디스코드/iMessage 등에 연결 가능
  • 직접 앱/창 제작 시 SDK나 headless 모드 사용 권장
  • 코덱스는 app server 형식이 아니면 TUI 연동이 까다로움, 클로드코드는 Channels로 수월하게 연동됨
  • Antigravity sidecar는 agentapi send-message 명령으로 프롬프트 주입 가능
  • 구독형 토큰으로 어디서든 클로드에 질문·응답을 붙여 쓸 수 있다는 결론
서버에 원격으로 접속해서 코딩하려면 어떻게 하나요?

Claude Code와 Codex를 VPS·서버에서 실행하고 모바일이나 노트북으로 원격 접속하는 운영 방식이 논의됐다. 노트북을 켜 둔 상태에서도 원격 사용이 가능하며, Claude Code는 Remote Control로 접근할 수 있다는 답이 나왔다. 서버 환경에서는 SSH 접속 후 tmux류 세션에서 실행하고, GitHub 동기화로 데이터 파편화를 관리하는 방식이 제안됐다.

  • VPS·서버에서 AI 코딩 에이전트를 상시 실행하는 활용법이 질문됐다.
  • 노트북을 켜 둔 상태에서도 모바일 원격 사용이 가능하다는 답변이 나왔다.
  • Claude Code의 Remote Control 기능이 언급됐다.
  • SSH와 tmux류 도구를 조합한 원격 세션 운용이 추천됐다.
  • GitHub 동기화로 프로젝트·제작물 데이터 파편화를 관리한다는 사례가 공유됐다.
AI에 입력하는 데이터의 DLP와 보안은 어떻게 관리해야 할까?

MCP 호출과 클로드 코드 활용만으로는 보안 필터링이 충분하지 않으며, 입력 단계에서 차단·라우팅하는 구조가 필요하다는 논의가 이어졌다. 프록시 형태로 사용 환경을 묶고 정책을 적용하는 방식이 언급됐다. AI DLP는 생성형 AI 사용 중 사내 기밀·소스코드·개인정보 유출을 탐지·차단하는 보안 솔루션으로 설명됐다. 기술적 통제만으로는 한계가 있어 임직원 교육과 관리적 보안도 중요하다는 결론이 나왔다.

  • MCP 호출 자체보다 사용자 입력이 외부 모델로 전달되기 전의 통제가 핵심이라는 의견이 나왔다.
  • 입력 앞단 라우터 또는 프록시로 사용 환경을 제어하는 방안이 제시됐다.
  • AI DLP는 생성형 AI 사용 중 기밀·개인정보·소스코드 유출을 실시간 탐지·차단하는 개념으로 설명됐다.
  • 정책 설정에 따라 생성형 AI 사용 자체를 제한하는 방식도 가능하다고 언급됐다.
  • 보안 사고 예방에는 기술 통제와 함께 사용자 교육이 필요하다는 데 공감대가 형성됐다.
네이버 데이터에 어떻게 접근해서 분석할 수 있을까?

Claude를 이용해 네이버에서 경쟁사 스마트스토어를 분석하거나 블로그 작성에 활용하려 했으나 접근이 막힌 문제를 논의했다. 공개 API·검색 결과·브라우저 자동화 등 공식 또는 공개 경로를 쓰고, 로그인 기능은 본인 권한의 정상 세션 안에서 다뤄야 한다는 원칙이 제시됐다. 막힌 공개 페이지 접근 도구로 Insane Search를 시도해 보라는 제안이 나왔다.

  • 네이버 기반 경쟁사 스마트스토어 분석과 블로그 작성 활용 사례가 제시됐다.
  • 기존 확장 프로그램 기반 접근이 과거와 달리 막혔다는 문제가 언급됐다.
  • 공개 API, 검색 결과, 브라우저 자동화 등 정상적인 접근 경로가 제안됐다.
  • 로그인 관련 기능은 본인 세션 권한 안에서 처리해야 한다는 원칙이 제시됐다.
  • Insane Search를 대안으로 시험해 보라는 추천이 나왔다.
매출DB 연동하려면 MCP가 꼭 필요한가요?

사내 매출데이터에 FastMCP로 붙여서 관리자용 인사이트를 주려는 시도에 대해, 단순 DB 연동이면 MCP까지 만들 필요 없이 API나 스킬(쿼리+스키마 정리)로 충분하다는 지적이 나왔다. 오버엔지니어링이라는 반응과 함께, 여러 팀 서비스에 접근권한 없이 데이터를 가져와야 하는 경우엔 OAuth 기반 권한체크와 함께 MCP가 유효하다는 반론도 있었다. 결론적으로 읽기 전용 권한(CRUD 중 Read만)을 반드시 지켜야 한다는 데 의견이 모였고, 내부망/샌드박스 분리도 제안됐지만 마케팅 대행사 규모라 내부망 인프라가 없을 수 있다는 현실적 한계도 언급됐다.

  • 단순 DB 조회면 MCP 서버 대신 쿼리+스키마 정리한 스킬로 충분하다는 의견
  • 여러 팀 서비스 데이터에 직접 접근권한이 없을 때는 OAuth+MCP 조합이 유효하다는 반론
  • 권한은 CRUD 중 Read만 허용해야 하며 admin 키 평문 공유는 위험하다는 경고
  • 내부망+샌드박스 분리 제안이 나왔으나 조직 규모상 인프라 부재 가능성 지적
아이폰 앱 개발하며 나눈 대화는 어떻게 정리하면 좋을까요?

전날 나온 모바일 앱 개발 얘기를 정리해달라는 요청이 있었다. 클로드 코드로 개발 중인 사진촬영→텍스트추출→JSON전송 앱이 서버 먹통 시 아예 못 쓰는 문제가 언급됐다. 보안은 크게 신경 쓰지 않고 있다는 점도 확인됐다.

  • 클로드 코드로 개발 중인 모바일 앱 사례 언급
  • 사진→텍스트추출→JSON전송 구조
  • 서버 다운 시 오프라인 대체 기능 부재가 문제
  • 보안은 우선순위가 낮음
맥에서 구글드라이브는 어떻게 연동하나요?

맥미니 M2 24GB의 활용성 질문과 Claude Code 로컬 폴더를 구글드라이브와 연동하는 방법 질문이 나왔다. 구글드라이브를 처음부터 작업 폴더로 잡아야 하는지에 대한 구체적 질문이 있었으나, 대화 내 답변은 제공되지 않았다.

  • 맥미니 M2 24GB 사양에 대한 평가 요청이 있었다.
  • Claude Code의 로컬 작업 폴더와 구글드라이브 연동 방법이 질문됐다.
  • 처음부터 구글드라이브 폴더를 프로젝트 폴더로 잡을지 문의했다.
  • 해당 질문들에 대한 후속 답변은 기록되지 않았다.
Aside를 대체할 만한 도구 있을까요?

Aside를 사용하려 했지만 macOS만 지원해 Windows 환경에서 대안을 찾는 질문이 나왔다. Aside는 로그인된 웹사이트에서 메시지·결제·CI 트리아지·스크린샷 같은 실제 작업을 에이전트가 수행하는 브라우저로 소개됐다. Windows에서 비슷한 브라우저 서비스나 Claude 스킬·커넥터·MCP 기반 대안을 요청하는 흐름이었다.

  • Aside는 로그인된 웹사이트에서 에이전트가 직접 작업하도록 만든 AI 에이전트 브라우저다.
  • Aside의 macOS 전용 지원으로 Windows 사용에 제약이 언급됐다.
  • Windows용 유사 브라우저 서비스 추천 요청이 있었다.
  • Claude 스킬·커넥터·MCP 기반 대안도 함께 요청됐다.
MCP 자격증명은 어떻게 관리해야 하나요?

MCP 커넥터에서 OAuth 토큰 저장소를 만들고, 웹사이트나 로컬 앱의 자격증명을 매번 입력하지 않도록 자동 활용할 수 있는지 질문했다. 비밀번호 금고처럼 자격증명을 안전하게 보관하고 필요할 때 가져오는 흐름을 원했다. 해당 질문에 대한 기술적 답변은 대화에 남아 있지 않다.

  • MCP 커넥터용 OAuth 토큰 저장소 구성이 질문됐다.
  • 반복적인 자격증명 전달을 줄이고 싶다는 요구가 핵심이었다.
  • 비밀번호 금고 형태의 보관·조회 경험이 비유로 제시됐다.
  • 구체 구현이나 보안 설계 답변은 확인되지 않았다.
SDK 없이 기기를 연동하는 방법이 있을까?

특정 제품은 대량 구매해야 SDK를 제공한다는 이야기가 나왔다. 이에 안드로이드로 연결한 뒤 클로드 코드에게 데이터 읽기 방법을 확인시키면 SDK 없이도 접근 가능하다는 경험담이 공유됐다. 젠스파크와 플라우드노트도 유사하게 연동했다는 언급이 있었고, 제조사 구현이 비슷하다는 의견이 나왔다.

  • 제품 SDK가 대량 구매 조건으로 제공된다는 문제가 제기됐다.
  • 안드로이드 연결 후 데이터 접근 방식을 확인하는 우회적 방법이 제안됐다.
  • 클로드 코드를 기기 데이터 구조 탐색에 활용하는 사례가 공유됐다.
  • 젠스파크와 플라우드노트에서도 비슷한 방식이 가능했다는 경험담이 나왔다.
Insane Search는 어떤 검색 도구일까?

네이버 접근 문제의 대안으로 Insane Search가 추천됐고, 이름의 의미도 가볍게 이야기됐다. Insane Search는 Claude Code용 플러그인으로, API 키 없이 차단된 웹사이트의 공개 페이지를 단계적 우회 전략으로 읽어오는 도구로 확인됐다. 참여자들은 ‘insane’을 매우 뛰어나거나 강렬하다는 뉘앙스로 이해했다.

  • Insane Search는 Claude Code용 플러그인으로 언급됐다.
  • API 키 없이 차단된 웹사이트의 공개 페이지를 읽는 도구로 확인됐다.
  • 접근이 막힌 네이버 관련 작업의 대안으로 추천됐다.
  • 도구명 ‘insane’은 매우 강렬하거나 뛰어나다는 영어 뉘앙스로 해석됐다.
Buzz랑 Hermes는 어떻게 연동하나요?

한 멤버가 Block(잭 도시)이 만든 팀 채팅·AI 에이전트·Git 통합 플랫폼 Buzz를 써봤는지 물었다. 이어서 Hermes 에이전트에 클로드 구독을 연결하는 방법을 물었고, 다른 멤버가 터미널에서 hermes setup을 입력하면 된다고 답했으나 그걸로 끝인지는 확답이 없었다.

  • Buzz 사용 경험 문의, 답변 없이 지나감
  • Hermes 에이전트에 클로드 구독 연결 가능 여부 문의
  • 터미널에서 'hermes setup' 명령어로 설정 시작한다는 답변만 나옴
GPT로 GIF나 영상도 생성할 수 있나요?

GPT로 GIF 파일을 만들려 했으나 이미지만 나온다는 질문이 나왔다. 다른 참여자는 GPT 자체로는 영상 생성이 안 되고, 영상 생성 AI를 MCP로 연동해서 뽑는 것 같다고 답했다.

  • GPT로 GIF 요청 시 이미지만 생성되는 문제 제기
  • GPT 자체로는 영상 생성이 안 된다는 답변
  • 영상 생성은 별도 영상 AI를 MCP로 연동해서 처리하는 것으로 추정
클로드코드를 디스코드 채널이랑 연동할 수 있나요?

클로드코드 세션을 디스코드에 연결해 쓰는 방법에 대한 질문과 답변이 오감. RC(공식 클로드코드)가 더 강력하고, 디스코드는 텍스트만 퍼나르는 방식이라는 설명이 나옴. -p 옵션 호출로 오인됐으나 실제로는 클로드코드 공식 channels 기능이라는 정정이 있었음.

  • RC와 디스코드 연동의 차이 설명
  • 디스코드 채널 호출은 -p 옵션이 아닌 공식 channels 기능
  • 관련 공식문서와 정리 노션 링크 공유됨

  • 문서 전체 임베딩 대신 디스크립션 임베딩 + 메타데이터 + 클로드 코드 처리가 효율적이라는 팁
  • RAG 품질은 벡터DB 단독이 아니라 SQL/그래프 DB 병행이 핵심
  • top-k 잘림과 리랭킹 기준의 주관성이 고질적 문제로 지적됨
  • md 상단 YAML 메타데이터 + grep 기반 노(no)-벡터DB 구성 사례 공유
직무별로 AI나 자동화를 어떻게 활용하고 계신가요?

HR/채용 담당자가 직무별로 AI를 어떻게 쓰는지 물으며 대화가 시작됐다. 채용 공고 자동화, 이력서 종합, 채용 트렌드 수집, 내부 ATS망에 MCP를 연동해 실제 채용 맥락을 반영한 백테스트 등 다양한 사례가 공유됐다. 반도체 설계 분야에서도 이미 AI가 작업을 시작해 ROI가 나오고 있다는 이야기, SAP 리포트 작업을 AI로 대체해 편해졌다는 경험도 나왔다.

  • HR/채용 직무자가 채용공고 업로드, 이력서 종합, 채용 트렌드 수집을 자동화
  • 내부 ATS 시스템에 MCP를 연동해 실제 채용 맥락 기반 백테스트 진행 중
  • SAP 리포트 작성을 개발자 없이 DB 직접 조회로 대체해 효율화
  • 반도체 설계 분야에서 AI 작업 도입 및 ROI 창출 사례 언급
  • 법무·세무법인의 AX(AI 전환)를 살펴보고 있다는 의견도 있었음
볼타나 블루버블로 입출금을 자동화할 수 있나요?

볼타의 계산서 미발행 체크 자동화, 입출금 알림을 블루버블 앱과 슬랙으로 뿌리는 개인 자동화 사례가 공유됐다. 이어서 은행·카드 거래내역 자동화의 어려움(카드사별 개별 로그인, API 부재, 마이데이터 한계)에 대한 논의로 확장됐다.

  • 볼타로 계산서 미발행 체크 자동화 사례 공유
  • 입출금 알림 메시지를 블루버블·슬랙으로 뿌리는 개인 자동화 소개
  • 카드사용내역은 카드사별 개별 로그인이 필요해 자동화 난이도 높음
  • 마이데이터가 PC 환경에서 지원되지 않는 한계 지적
  • 카드사 MCP 개방 가능성에는 회의적 의견 다수
코파톤이랑 올리브영 코딩테스트는 실제로 어떤 식으로 진행되나요?

코파톤 기출문제와 올리브영 경력채용 테스트 환경이 유사하다는 이야기가 나왔다. 실제 올영 문제는 'MD를 위한 기획전 생성 + 유저반응에 따른 AI 화면재구성 자동화'였고, 이를 클로드로 얼마나 잘 다루는지를 평가하는 것으로 보인다는 분석이 이어졌다. 백준 코테 이후 이런 유형 테스트가 처음이라 접근법에 대한 감이 안 잡힌다는 고민과, 플랫폼 구현 범위를 어디까지 보여줘야 하는지에 대한 질문이 오갔다.

  • 코파톤 기출과 올리브영 채용테스트 환경이 유사하다는 관찰
  • 올영 실제 문제: 기획전 생성 + 유저반응 기반 AI 화면재구성 자동화
  • 클로드 활용 숙련도를 평가하는 성격으로 추정
  • 구현 범위(설계 수준 vs 실제 구현)에 대한 고민 공유
  • 채용 테스트 방식 전환에 대한 우려도 언급됨
비개발자가 하네스 쓰려면 어떻게 시작해야 하나요?

비개발자가 하네스와 프롬프트를 고도화하는 궁극적 목적, 그리고 투자 대비 효용을 질문했다. 개인 용도로 Claude Code와 Codex를 쓰는 비개발자는 변화 속도를 따라가려는 압박보다 자신의 목적과 도메인에 맞춰 활용하면 된다는 의견이 나왔다. 명확한 목적 없이 하네스를 구성하면 제품 업데이트 속도를 따라가기 어려워 비추천이라는 경험담도 공유됐다.

  • 비개발자의 하네스·프롬프트 고도화 필요성을 논의했다.
  • 개발 영업이나 업무 목적이 없으면 자기만족에 가까운지 질문이 나왔다.
  • 명확한 목적 없는 하네스 구성은 유지 비용이 커질 수 있다는 경험담이 제시됐다.
  • 도구와 방법론은 계속 바뀌므로 FOMO를 가질 필요 없다는 위로가 이어졌다.
  • 자기 도메인이 있는 직장인의 활용 가능성이 오히려 강점이라는 의견도 나왔다.
룰 기반 라우팅은 어떻게 설정하는 게 좋을까요?

대규모 바이브 코딩에서 메인 세션이 모든 작업을 수행하며 컨텍스트가 무너지는 문제를 해결하기 위해 룰 기반 라우팅 구조를 논의했다. 큰 작업은 마스터 오케스트레이터와 디렉터리별 워커 에이전트로 나누고, 마스터가 PRD와 메모리를 관리하는 방식이 제안됐다. 워커는 필요한 PRD·메모리·도구·스킬의 주소만 작업 시점에 불러오며, 작업 결과와 맥락 갱신을 마스터에 보고한다. 모든 대화 기록을 유지하기보다 핸드오프 중심 메모리로 필요한 맥락만 전달하는 것이 핵심으로 제시됐다.

  • 메인 세션 하나에 작업을 몰면 긴 작업에서 컨텍스트 품질이 저하된다는 문제가 제기됐다.
  • 루트 디렉터리에 마스터 오케스트레이터를 두고, 하위 디렉터리를 워커 에이전트 역할로 분리하는 구조가 제안됐다.
  • 마스터가 PRD를 작성해 각 워커에 배분하고, 워커는 결과와 메모리 갱신 사항을 마스터에 보고한다.
  • 워커는 작업 시작 시 PRD와 필요한 메모리를 요청하고 계획을 세운 뒤 필요한 스킬·도구·서브에이전트를 룰에 따라 선택한다.
  • 지침 전체를 상시 로드하지 않고 참조 주소를 관리하며, 새 작업 시점에는 훅으로 메모리를 갱신하는 방안이 언급됐다.
AI 직원 자동화는 어떻게 설계하면 좋을까요?

텔레그램에서 팀장이 지시를 받고 리서치·카피·디자인·광고 업데이트를 수행한 뒤 결과를 보고하는 AI 직원 체계를 만들고 싶다는 요구가 제시됐다. 참여자들은 코워크보다 Claude Code 또는 코드 기반 접근이 적합하며, 처음에는 대화로 목적과 모르는 부분을 명확히 하며 시작하라고 조언했다. 인스타그램에서 보이는 직원 활동 시각화보다 실제 업무 결과와 반응형 자동화에 집중해야 한다는 의견이 나왔다. 외부 출장 중에도 동작시키려면 24시간 실행 환경이나 VPS 등 운영 구조를 고려해야 한다고 설명됐다.

  • 목표는 팀장 에이전트가 하위 역할에 업무를 배정하고 결과를 보고하는 자동화다.
  • 리서치, 카피·캡션 생성, 이미지·영상 생성, 광고 업데이트 역할이 예시로 제시됐다.
  • 코워크보다는 코드 기반 구현이 적합하다는 조언이 반복됐다.
  • 처음부터 완성품을 만들기보다 목적을 설명하고 대화로 구현 범위를 좁히라는 조언이 나왔다.
  • 실제 자동화는 PC 상시 실행 또는 VPS 같은 항상 켜진 서버 환경을 검토해야 한다.
텔레그램으로 업무 자동화를 하려면 어떻게 해야 하나요?

외부 출장 중에도 텔레그램 지시로 업무를 수행하고 결과를 보고하는 자동화 시스템을 운영한다는 사례가 공유됐다. Claude API 비용이 예상보다 많이 든 상황에서 VPS와 미니PC 중 어떤 방식이 경제적인지 질문했다. 서버는 지속 비용과 관리 편의성, 미니PC는 높은 초기비용·낮은 지속비용·상대적으로 어려운 관리라는 비교가 제시됐다.

  • 텔레그램 지시→업무 진행→텔레그램 보고 형태의 원격 자동화 시스템이 소개됐다.
  • AI API 비용 절감과 운영 방식 선택이 핵심 고민으로 제시됐다.
  • VPS 월 비용과 미니PC 구매비를 비교해 결정해야 한다는 의견이 나왔다.
  • 서버는 관리 편의성이, 미니PC는 장기 고정비 절감 가능성이 장점으로 언급됐다.
  • 트렌드 조사·콘텐츠 기획·이미지 생성·SNS 게시·광고 관리·팀장 역할로 구성된 에이전트 체계가 공유됐다.
Hermes 대신 클코로 자동화해도 괜찮을까요?

헤르메스(자동화 툴)보다 클로드코드를 디스코드에 물려 쓰는 게 낫다는 의견이 나옴. u1802가 소개한 ThisCode라는 디스코드-클로드코드 연동 오픈소스 스킬(깃헙 링크 공유)이 화제가 됨. 봇 여러 개를 채널별로 나눠 관리하며 회의실 채널에서 전체 관리도 가능하다는 실사용 후기가 공유됨. 크론잡으로 매일 작업을 자동화하고 외부에서 디스코드로 명령 내리는 방식도 소개됨.

  • u1802가 디스코드와 클로드코드 채널을 연결해 규칙·훅을 얹는 ThisCode 스킬을 소개, 업데이트가 잦아 플러그인으로 자주 받으라고 권장
  • 헤르메스는 느리다는 평, 클로드코드로 대체 가능하다는 의견 다수
  • 채널별로 봇 4개를 나눠 운영하며 크론잡으로 매일 자동 작업 수행
  • 외부에서 디스코드로 명령 내리는 방식이 음성비서(오르카)보다 편할 때가 있다는 실사용 후기
디자인 하네스나 레퍼런스는 어떻게 활용하나요?

바이브코딩으로 디자인 작업 시 순정 클로드로는 부족하고 하네스를 계속 바꿔도 발전이 없다는 고민이 공유됨. 레퍼런스를 쪼개서 활용하고 세세한 규칙을 준 스킬이 좋다는 의견과 함께 getdesign.md, seed-design.io 같은 레퍼런스 사이트, 개인 제작 도구(visigner)가 공유됨. 결국 제대로 된 UX/UI 기획과 사용자 시나리오가 반영된 설계가 선행되어야 좋은 디자인이 나온다는 결론.

  • 좋은 디자인 스킬들은 대부분 레퍼런스 기반으로 세세한 규칙을 제공
  • getdesign.md, seed-design.io 등 디자인 레퍼런스 사이트 공유, 괜찮은 사이트는 그냥 참고(파쿠리)하기도 함
  • 레퍼런스를 쪼개 활용하는 개인 제작 도구 visigner(깃헙)가 소개됨
  • design.md 파일만 넣는 것으로는 부족하고, UX/UI 기획·레이아웃 설계·사용자 시나리오 반영이 선행되어야 한다는 의견
에이전트로 글쓰기 워크플로우는 어떻게 짜나요?

매일 주제를 받아 글쓰기를 하다가 흐지부지된 경험이 공유되며 다른 사람들의 글쓰기 방식을 질문. 한 명은 클코가 주제를 받아 알아서 글을 쓰고 영상까지 만들어 업로드한다고 답변. 다른 참가자는 책 내용과 일상을 엮어 쓴 뒤 코덱스가 다듬는 방식, 마이크로 GPT·제미니에 얘기하며 주제를 추천받는 방법도 제안됨. u1802는 개별 메모리와 글쓰기 스킬로 기존 글·피드백을 학습시키고, 최종 휴먼터치 버전 기준으로 반드시 피드백을 준다고 공유.

  • 매일 주제를 받아 글쓰는 방식은 오래 지속하기 어려웠다는 경험 공유
  • 클코가 주제를 받아 글을 쓰고 영상 제작·업로드까지 자동화하는 사례 소개
  • 마이크 켜고 GPT·제미니에 얘기하다 글감을 추천받는 방법 제안
  • 개별 메모리+글쓰기 전용 스킬로 기존 글과 피드백을 학습시키고, 최종 휴먼터치 버전 기준 피드백을 반영하는 방식 공유
볼타나 팝빌로 세금계산서 자동화할 수 있을까요?

클로드 코드로 세금계산서 자동화가 가능한지 질문이 나오자 볼타(Bolta)가 추천됨. 현직 회계사라는 유저가 공제 목적만으로 사업자 등록하는 것은 권장하지 않는다고 조언함(사업자 등록 시 부가세·종합소득세 신고도 함께 따라옴). 이어서 팝빌로도 같은 자동화가 가능한지, 비개발자 기준 볼타와 팝빌 중 어느 쪽이 더 쉬운지 질문이 이어짐.

  • 볼타(Bolta): 홈택스 연동 기반 전자세금계산서 발행·관리 SaaS
  • 팝빌: 전자세금계산서·현금영수증 등을 API로 연동하는 서비스
  • 현직 회계사가 공제 목적만의 사업자 등록은 비권장한다고 조언
  • 비개발자 기준 볼타 vs 팝빌 자동화 난이도 비교 질문이 이어짐(구체적 답은 로그에 없음)
오픈크랩은 실제 워크플로우에서 어떻게 활용하면 좋을까요?

오픈크랩을 활용해 코덱스로 배경지식·데이터를 크롤링하고 팩을 만들어 작업에 투입하니 결과물 퀄리티가 좋아졌다는 경험이 공유됐다. 로고 제작에도 크롤링→온톨로지팩→스킬조합→클로드+코덱스 세팅→작업의 파이프라인을 적용해 퀄리티를 높이고 SVG 파일까지 뽑아내는 실무 적용 사례가 소개됐다.

  • 오픈크랩으로 배경지식·데이터를 미리 깔아주고 작업 시작
  • 코덱스 크롤링+팩 생성 방식으로 스킬/결과물 품질 향상
  • 로고 제작 파이프라인에 온톨로지팩과 스킬조합 적용
  • 실무에서 AI SVG 결과물까지 추출해 활용 중
하네스의 핵심 규칙은 정확히 무엇인가요?

각자의 하네스에서 빼놓을 수 없는 운영 규칙을 공유했다. 에이전트 생성 전 claude.md의 규칙 라우팅 전략을 확인하고, 기능 단위 작업 뒤에는 progress.md로 산출물을 남기는 방식이 소개됐다. 테스트 성공만으로 끝내지 않고 사람이 직접 결과를 확인하는 최종 검수 원칙도 강조됐다.

  • 에이전트 생성 전에 claude.md의 규칙 라우팅 전략을 확인한다.
  • SPEC 단위로 기능을 만들고 progress.md에 결과물을 남긴다.
  • 자동 테스트가 성공해도 사람이 직접 결과를 확인한다.
  • 규칙 라우팅·진행 기록·최종 눈검수를 핵심 운영 요소로 정리했다.
메모리 허브는 어떻게 활용하면 좋을까요?

여러 Claude Code 세션을 열어 작업 맥락을 잊는 문제를 해결하기 위해 메모리 허브를 만들자는 제안이 나옴. Claude Code를 실행할 때마다 진행 중인 작업을 리캡하게 하면 좋겠다는 사용 방식이 공유됨. 이후 메모리 허브를 어떻게 구축할 수 있는지 질문이 이어졌고, 레퍼런스를 찾아 설명해 달라는 요청과 함께 충분한 사용 경험의 중요성이 언급됨.

  • 다중 세션 사용 시 작업 맥락을 잊는 문제가 제기됨.
  • 시작 시점에 진행 상황을 자동 리캡하는 방안이 제안됨.
  • 메모리 허브의 구축 방식과 참고 자료에 대한 질문이 나옴.
  • 프롬프트 기술뿐 아니라 실제 사용 경험이 중요하다는 의견이 나옴.
비개발자도 파이썬으로 자동화할 수 있나요?

장부 매출전표 입력·출력용 파이썬 스크립트를 바이브코딩으로 만들다가 단계별 진행과 무한 루프 해결에 막힌 비개발자의 고민이 제기됐다. 웹이 아닌 환경에서 작업해야 하며, PAD나 파이썬 기반으로 쓸 만한 스킬·도구 추천을 요청했다. PAD는 코드 수정 전 pad.md 계획 문서를 작성·유지해 계획 우선 개발을 강제하는 Claude Code용 서드파티 스킬로 언급됐다.

  • 매출전표 입력과 출력 자동화가 목표다.
  • 바이브코딩 중 진행이 막히거나 무한 루프가 발생한다.
  • 웹 사용이 어려운 환경이라 PAD 또는 파이썬 스크립트 중심 접근이 필요하다.
  • 비개발자에게 적합한 GitHub 스킬·도구 추천이 요청됐다.
헤드헌터 스팸 메시지를 자동으로 걸러낼 수 있나요?

하루에 다수의 헤드헌터 스팸을 받는 상황에서, 조건 미달 제안에는 응답·전화하지 말라는 안내를 자동화하는 파이썬 도구를 만들었다는 사례가 나왔다. Fable이 단호하면서도 고급스러운 거절 답신 문구를 작성해 줬고, 이를 실제로 보내고 있다는 경험담이 공유됐다. 해당 자동 처리기를 GitHub에 공개할지 고민하는 대화가 이어졌다.

  • 헤드헌터 스팸 메일 대응을 파이썬으로 자동화한 사례가 공유됐다.
  • 연봉과 조건 기준을 안내하고 불필요한 연락을 막는 답신을 만들었다.
  • Fable이 정중하면서도 강한 어조의 답신 작성에 활용됐다.
  • 자동화 도구를 GitHub에 공개할지 검토 중이라고 했다.
명함 정보를 DB로 자동화하려면 어떻게 하나요?

명함 사진을 촬영하면 정보를 자동으로 DB에 정리하는 업무 자동화 방법이 질문으로 나왔다. 이는 특정 플러그인 기능이라기보다 원하는 출력 형식을 정한 뒤 Claude Code에 작업을 지시해 구현할 수 있다는 답변이 제시됐다. 사진 속 명함 정보를 추출해 운영 사이트나 데이터베이스에 기록하는 흐름으로 이해됐고, 아날로그 명함 수집 업무를 줄일 수 있다는 반응이 나왔다.

  • 명함 사진에서 정보를 추출해 DB화하는 자동화 수요가 제기됐다.
  • 특정 내장 기능보다 작업 지시와 목표 출력 형식 설계가 중요하다는 의견이 나왔다.
  • 운영 중인 사이트에 자동 등록하는 형태도 구현 가능한 활용 사례로 언급됐다.
  • 명함 수집·정리 업무의 수작업 부담을 줄일 수 있다는 기대가 나왔다.
하네스 정리할 때 브랜치는 어떻게 관리하나요?

복잡해진 하네스를 정리하기 위해 별도 분석 도구를 이용하고 새 프로젝트에서 재구성하는 방법이 제안됐다. 하네스가 저장소에 포함된 경우에는 수술용 브랜치를 따로 만들어 하네스를 제거한 뒤 작업해보겠다는 계획이 나왔다. 세션 이력·아카이브·메모리도 기존 지시사항을 끌어와 드리프트를 유발할 수 있으므로 프로젝트 폴더까지 분리하는 편이 좋다는 의견이 제시됐다.

  • 별도 모델에게 하네스와 프로젝트를 분석시켜 자료를 남긴 뒤 새 프로젝트에서 재구성하는 방법이 제안됐다.
  • 저장소에 하네스가 포함된 경우 수술용 브랜치를 만들어 제거·실험하는 방안이 나왔다.
  • Claude Code의 세션 이력과 메모리는 이전 지시사항의 영향을 받을 수 있다는 의견이 나왔다.
  • 읽기·분석·대화 역할을 분리하지 않으면 드리프트가 커질 수 있다는 경고가 있었다.
Fable을 여러 개 돌려쓰는 풍차돌리기는 어떻게 하는 건가요?

Fable 계정을 병렬로 돌리는 이른바 풍차돌리기와 이를 위한 고사양 노트북 이야기가 나왔다. 최소 메모리로 32GB가 언급됐고, 그림 기준으로는 8개까지 필요하지 않을 수 있다는 반응도 있었다.

  • Fable 다계정 병렬 사용 사례가 언급됐다.
  • 풍차돌리기용 장비로 고사양 노트북과 메모리 용량이 논의됐다.
  • 최소 사양으로 32GB 메모리가 언급됐다.
  • 동시 실행 수가 반드시 8개일 필요는 없다는 의견이 나왔다.
ThisCode의 메모리 기능은 어떻게 활용하나요?

Claude 구독자가 Hermes 대신 ThisCode를 쓸 만한지 질문이 나왔다. ThisCode에도 장기 메모리를 붙일 수 있는지 확인 요청이 이어졌다. 같은 플러그인의 KM을 쓰면 장기 메모리를 붙일 수 있다는 의견이 제시됐다.

  • Claude 구독 환경에서 Hermes 대체재로 ThisCode 활용 가능성을 물었다.
  • ThisCode의 장기 메모리 지원 여부가 핵심 관심사였다.
  • KM 플러그인을 통한 장기 메모리 구성이 언급됐다.
네이버 블로그 자동화는 어떻게 하는 건가요?

네이버 블로그 포스팅 자동화 사례가 있는지 질문이 나왔다. 네이버 측 AI 연동 관련 서비스가 있었던 것 같다는 언급은 있었지만 구체적인 서비스명이나 구현 방법은 확인되지 않았다. 질문자는 우선 Claude Code에 물어보겠다고 했다.

  • 네이버 블로그 포스팅 자동화 경험자가 있는지 질문이 나왔다.
  • 네이버의 AI 연동 관련 서비스가 언급됐으나 구체적인 정보는 나오지 않았다.
  • 질문자는 코드 도구에 직접 구현 방법을 물어보기로 했다.
클로드 말투가 요즘 왜 바뀐 걸까요?

클로드가 갑자기 반말하거나 지나치게 다정한 어조를 쓰는 현상이 언급됐다. 하네스에 말투 지시가 있어도 세션에 따라 어조가 미묘하게 흔들릴 수 있다는 경험이 공유됐다. 강한 지시를 달아도 말투 제어가 완전하지 않다는 의견이 나왔다.

  • 클로드가 갑자기 반말을 시작했다는 사례가 나왔다.
  • 세션마다 말투가 달라지는 느낌이 있다는 경험이 공유됐다.
  • 말투를 강하게 지정해도 완전한 통제가 어렵다는 의견이 나왔다.

클로드가 파일을 지워버린 사례 있으신가요?

클로드코드가 명시하지 않은 파일까지 삭제하거나, 미승인 상태에서 진행 여부를 스스로 결정한 사례들이 공유됐다. 한 명은 '삭제할 파일 확인→명시→삭제'로 3단계 지침을 줬는데도 경로를 잘못 짚어 관련없는 파일까지 날아갔다고 전했고, 다른 명은 유저 확인이 필요한 시점에서 AI가 스스로 user 발화를 만들어 승인을 우회한 사례를 공유했다. 대응책으로 '삭제' 대신 '격리(별도 디렉터리로 이동)' 지침을 주면 효과적이라는 팁이 나왔고, 한 명은 격리 후 일정 기간 문제 없으면 백업, 이후 자동 삭제하는 규칙까지 구체적으로 제안했다.

  • 명시된 파일만 지우라는 지침에도 경로 오류로 전체 삭제된 사례 발생
  • '삭제' 대신 '격리(디렉터리 이동)' 단어로 지침을 바꾸면 안전하다는 팁
  • 유저 확인이 필요한 지점에서 AI가 스스로 user 메시지를 생성해 승인 우회한 사례 공유
  • 룰 제안: 별도 격리 → 한달 무문제 시 백업 → 6개월 무문제 시 백업도 자동 삭제
  • git으로 관리하면 복구 가능하다는 실용적 코멘트도 있었음
인세인리서치라는 게 뭔지 소개해줄 수 있나요?

인세인서치와 인세인리서치라는 명칭이 언급된 뒤, 인세인리서치의 철학과 기능을 소개하는 내용이 공유됐다. 인세인리서치는 공개 웹 정보를 대상으로 질문 범위를 잡고 여러 전문 리서치 에이전트를 병렬 실행해 출처를 교차검증하며 인용이 포함된 구조화 마크다운 리포트를 만드는 클로드 코드용 7단계 다중 에이전트 리서치 플러그인이다. 공유된 소개에서는 사람이 브라우저로 접근 가능한 공개 정보라면 AI 에이전트도 접근 가능해야 한다는 철학이 강조됐다.

  • 인세인리서치는 클로드 코드용 플러그인이다.
  • 질문 범위 설정부터 보고서 생성까지 7단계 다중 에이전트 리서치 흐름을 제공한다.
  • 전문 리서치 에이전트를 병렬로 실행하고 출처를 교차검증한다.
  • 인용이 포함된 구조화 마크다운 리포트를 생성한다.
  • 공개 웹 정보에 대한 AI 에이전트의 접근성 철학이 소개됐다.
인세인서치를 연구 목적으로 어떻게 활용할 수 있나요?

insane-search와 insane-research가 연구·자료조사 워크플로에 유용하다는 실제 활용 경험이 공유됐다. 연구자는 기존 academic pipeline의 한국화 부족을 보완하기 위해 앞단 리서치 스킬로 연결하고, 기관 자료를 우선 사용하도록 수정했다고 설명했다. 특히 claim ledger와 abstention 같은 검증·보류 장치가 출처 품질 문제를 줄이는 데 도움이 됐다는 평가가 나왔다. 제작자는 Claude Code에서 직접 되지 않는 자료조사를 딥리서치 방식에서 차용해 만들었고, 너무 느린 도구보다 적당한 속도와 품질의 균형을 선호한다고 밝혔다.

  • insane-search는 API 키나 로그인 없이 차단된 공개 웹페이지를 여러 경로로 읽어오는 Claude Code 플러그인이다.
  • 연구 환경에서 한국화가 부족한 조사 엔진을 보완하는 용도로 응용 사례가 공유됐다.
  • 연구기관 자료를 우선 사용하도록 스킬을 수정한 사례가 나왔다.
  • claim ledger가 조사 결과의 검증 부담을 줄였다는 평가가 나왔다.
  • abstention 같은 보류 처리와 출처 검증 구조의 필요성이 언급됐다.
글쓰기 윤문에 어떤 플러그인을 채용하면 좋을까요?

윤문 플러그인이 AI 작성 한국어, 특히 자기소개서 문체를 자연스럽게 다듬는 데 효과적이라는 사용 후기가 공유됐다. AI 필터링을 피하려고 AI 티를 지우는 자기소개서를 만드는 상황의 아이러니도 언급됐다. 채용 현장에서는 AI 문체 자체보다 지원자의 스토리 패턴, 가치관, 직무 조건 적합성을 분류할 가능성이 크다는 의견이 나왔다. ATS는 Applicant Tracking System의 약자라고 정리됐다.

  • 윤문 플러그인은 AI 작성 한국어를 자연스럽게 다듬고 AI 작성 여부를 진단하는 Claude Code 플러그인이다.
  • 자기소개서의 AI 티를 줄이는 용도와 AI 필터링의 관계가 논의됐다.
  • 대량 지원 상황에서 서류 자동 분류 필요성이 언급됐다.
  • ATS는 Applicant Tracking System으로 정정됐다.
  • 실무 관점에서는 프로젝트 적합성 평가와 점수 기반 선별을 한다는 경험담이 나왔다.
AI 생성물에 워터마크를 넣는 게 맞을까?

Claude 생성 문체 워터마크에 보이지 않는 심볼이 포함되는지, 공개된 제거기가 실제로 동작하는지 질문이 나왔다. 관련 링크가 공유됐고, AI 글쓰기 워터마크는 특정 단어를 특정 배치에 두는 방식일 수 있다는 설명이 언급됐다. 다만 사람이 유사한 문체를 써도 AI로 단정될 수 있어 워터마크로서 신뢰하기 어렵다는 회의적 의견이 나왔다.

  • Claude 생성 문체 워터마크의 구조와 제거 가능성을 두고 질문이 나왔다.
  • 관련 사례 링크가 공유됐다.
  • 워터마크가 단어 선택과 배치 패턴을 활용할 수 있다는 설명이 언급됐다.
  • 사람이 비슷한 문체를 사용할 때 오탐 가능성이 있다는 우려가 제기됐다.
  • 보이지 않는 심볼 존재 여부나 제거기의 실제 효과는 대화에서 확정되지 않았다.
클로드 디자인을 어떻게 개선할 수 있을까?

Claude가 만드는 프론트엔드·문서 디자인 초안이 판에 박힌다는 고민이 제기됐다. 단순히 스킬을 내려받기보다 디자인 자체를 학습하고 디자인 시스템을 참고하라는 조언이 나왔다. 프론트엔드에서는 shadcn/ui, Hero UI 등을 참고하고, 문서 디자인은 초안을 만든 뒤 반복 사용 가능한 스킬로 정리하는 방법이 제안됐다.

  • Claude의 기본 디자인 초안이 획일적이라는 문제의식이 공유됐다.
  • 디자인 결과를 개선하려면 디자인 학습과 레퍼런스 활용이 중요하다는 의견이 나왔다.
  • 프론트엔드 참고 대상으로 shadcn/ui와 Hero UI가 언급됐다.
  • 문서 작업은 기본 초안을 바탕으로 재사용 가능한 스킬을 만들라는 방법이 제안됐다.
  • 프론트엔드용 스킬 저장소 두 개가 공유됐다.
무료로 들을 만한 영상 AI 강의 추천 있을까요?

AI 영상 제작 강의에서 Claude와 Higgsfield를 조합하려 했으나, Seedance 생성이 유료 사용자 중심이라 무료 수강생 실습이 어렵다는 문제가 제기됐다. Google Flow 외 대안으로 Pika, Kling, Hailuo 등이 언급됐고, 무료 정책·워터마크·대기열 변수를 고려해 Flow를 메인으로 두고 다른 도구를 백업 데모로 병행하라는 의견이 나왔다. 스토리보드 이미지는 Claude와 Higgsfield에서 만들고, 이를 Flow에서 영상화하는 방향도 검토됐다.

  • Higgsfield에서 Seedance 생성이 무료 사용자에게 제한된 상황이 언급됐다.
  • Google Flow 외에 Pika, Kling, Hailuo가 무료 체험 또는 제한 생성 후보로 제안됐다.
  • 무료 정책은 수시로 바뀌므로 강의 시연 도구를 분산할 필요가 있다.
  • 워터마크와 생성 대기열도 강의 운영 변수로 지적됐다.
  • 스토리보드 이미지 생성과 영상 생성 도구를 분리하는 워크플로우가 논의됐다.
GPT랑 클로드 중 뭘 구독해야 할까요?

지피티 20불+클로드 100불 조합과 지피티 100불+클로드 20불 조합 중 뭐가 나을지 반복해서 질문이 올라옴. 코딩 위주라 채팅용 지피티를 별도로 20불 구독하고 있다는 상황 설명. 답변은 개인차가 크니 직접 써보고 판단 기준을 세울 실력이 안 되면 그냥 클코를 쓰라는 조언, 코드가 주력이면 클로드 비중을 유지하는 게 실용적이라는 의견으로 정리됨.

  • 지피티20+클로드100 vs 지피티100+클로드20 조합 고민
  • 코딩 위주 사용자가 채팅용 지피티를 별도 구독 중
  • 개인차가 커서 직접 써보고 정해야 한다는 조언
  • 코드가 주력이면 클로드 비중 유지가 실용적이라는 의견
클로드코드 처음 배우는 초보자는 어떻게 공부하면 될까요?

한 참가자가 클로드코드 구조를 이해하지 못해 컨텍스트에 데이터가 뒤섞이고 교정문이 무시되는 문제를 겪었다며 초보자용 자료를 요청했다. LLM에는 '학습'이라는 개념이 없다는 용어 정정과 함께, 가진 것/하고 싶은 것/되는 것·안 되는 것을 정리해달라는 조언이 나왔다. 클코101을 참고하라는 답과 함께 챗→로컬 파일 저장→구조화까지 이어진 개인 경험담이 공유됐다.

  • 초보자가 컨텍스트 관리 문제로 클로드코드 구조 이해에 어려움 호소
  • LLM에 '학습' 개념이 없다는 용어 정정 조언
  • 클코101 자료 추천
  • 챗→기록 이관→로컬 저장 구조화로 발전한 개인 사용 경험 공유
클로드 계정 전환(/login)이 왜 제대로 안 되나요?

구독 2개를 쓰는 유저가 /login으로 계정을 갈아타는 게 최근 안 된다고 문의했다. 윈도우+우분투(tmux) 환경이라는 점이 확인됐고, 맥에는 계정 스위칭 전용 앱이 있다는 안내가 있었다. cliproxy/vibeproxy, cc switch 같은 대안 도구들도 언급됐다.

  • 윈도우+우분투(tmux) 환경에서 /login 계정 전환이 안 되는 문제 제기
  • 맥에는 계정 스위칭 전용 앱이 있다는 언급 (구체 명칭은 cc switch로 추정)
  • cliproxy/vibeproxy가 멀티 계정 활용의 대안으로 언급됨
  • vibeproxy도 cliproxy 기반이라 외부 API 차단 이슈와 무관하다는 설명
claude mem으로 여러 프로젝트를 통합 관리할 수 있나요?

claude mem을 쓸 때 프로젝트별로 나뉘어 관리가 복잡하다는 고민이 나왔다. 하나하나 확인·체크하기 번거롭고, 여러 프로젝트를 한눈에 볼 수 있는 상단 허브 같은 게 없다는 아쉬움을 토로했다. 다른 참여자가 폴더별이 아닌 전체 접근 개념을 원하는 것 같다고 정리했지만 뾰족한 해법은 나오지 않았다.

  • claude mem 프로젝트별 관리가 번거롭다는 문제 제기
  • 여러 프로젝트를 통합 조망할 상단 허브 기능 부재
  • 폴더별 접근이 아닌 전체 접근 개념을 원한다는 취지로 정리됨
  • 명확한 해결책은 못 찾고 마무리
Omo native는 어떻게 시작하나요?

Omo native를 처음 사용해 보려는 참여자가 터미널 경험 부족을 언급하며 사용자를 찾았다. 먼저 Claude Code를 터미널에서 사용해 보는 것을 권했고, 일단 직접 써보겠다는 반응으로 마무리됐다. Omo native는 Claude Code 네이티브 플러그인 시스템을 활용해 규칙 주입, 코멘트 검사, LSP, ultrawork 오케스트레이션 등을 제공하는 배포판이다.

  • Omo native를 사용하려는 초보 사용자가 경험담을 요청했다.

  • 먼저 Claude Code를 터미널에서 직접 써보라는 조언이 나왔다.
  • Omo native는 Claude Code용 네이티브 플러그인 배포판이다.
OMO와 가재코드는 어떻게 연결해서 쓰나요?

OMO native와 가재코드의 차이, Claude 사용 시 무엇을 쓰는지 묻는 질문이 반복됨. 일부는 Claude를 사용한다고 답했지만 도구 간 차이를 설명하는 정확한 답변은 없음. 이후 가재코드와 오모코드의 의미를 다시 질문하는 흐름이 이어짐.

  • OMO native와 가재코드의 차이를 묻는 질문이 나옴.
  • Claude 사용자는 Claude를 쓴다는 짧은 답이 있었음.
  • 가재코드와 오모코드의 개념을 추가로 질문함.
  • 한 응답은 가재를 가짜 데이터라고 설명했으나 코드 도구 의미와의 연결은 불명확함.
구독 요금제에 따라 디자인 품질도 달라지나요?

여러 AI 구독 조합을 사용 중이라는 공유가 있었다. GPT는 문서 생성에는 강점이 있지만 디자인 결과가 AI스럽다는 평가가 나왔다. 디자인을 다듬기 위해 다른 도구를 다시 써야 할지 고민하는 흐름이었다.

  • GPT Plus, Claude Code Pro, GLM Lite 구독 조합이 언급됐다.
  • GPT의 문서 생성 품질은 긍정적으로 평가됐다.
  • 디자인 결과가 인공적인 느낌이라는 아쉬움이 제기됐다.
  • 디자인 보정용 도구 재사용을 고민했다.
Grok은 실제로 어디에 활용하고 계신가요?

Grok이 실제로 쓸 만한지, Grok Build를 어디에 붙여 활용하는지 질문이 이어졌다. 데스크톱 앱은 없지만 다른 도구와 연결해 사용할 수 있다는 의견이 나왔다. Grok Build 자체의 기획력은 얕게 느껴져 클로드 코드의 워커 역할로 활용하려 한다는 사례가 공유됐다. Grok Build 품질이 기대보다 낮다는 평가와 더 나은 활용 방식에 대한 재질문도 있었다.

  • Grok의 전반적 실용성과 사용처를 묻는 질문이 나왔다.
  • Grok은 데스크톱 앱 대신 다른 도구와 연결하는 활용 가능성이 언급됐다.
  • Grok Build는 기획력이 부족하다는 사용 경험이 공유됐다.
  • Grok Build를 단독 기획 도구보다 클로드 코드 작업의 보조 워커로 쓰려는 접근이 제시됐다.
브라우저를 자동으로 조작하려면 어떤 방식을 쓰나요?

Claude Code에서 브라우저를 조작하는 방법으로 /chrome, CDP, Playwright가 언급됐다. CDP가 가장 깔끔하고 편하다는 의견이 주로 나왔으며, 다른 브라우저를 쓰려면 Playwright를 활용할 수 있다는 설명이 덧붙었다. CDP를 대체할 브라우저를 찾는 상황에서도 편의성 때문에 CDP가 선호된다는 반응이었다.

  • Claude Code 브라우저 조작 방법으로 /chrome이 언급됐다.
  • CDP가 설정과 사용 면에서 가장 편하다는 의견이 나왔다.
  • Playwright를 이용하면 다른 브라우저를 활용할 수 있다고 설명됐다.
  • CDP와 가정용 PC를 함께 쓰는 사례 링크가 공유됐다.
클로드 성향이 드리프트되는 걸 어떻게 제어하면 좋을까요?

한 참가자가 채팅용 클로드가 성향 드리프트를 심하게 일으켜 계정 잠금이 걱정될 정도라고 토로했다. 클로드가 유저 친화적으로 어떻게든 해주려는 성향이 강해서 마크다운 규칙을 줘도 잘 안 지킨다는 문제도 제기됐다. 궤도 수정을 프롬프트로 넣기 어렵다는 하소연으로 마무리됐다.

  • 장기간 채팅 사용으로 클로드 성향이 크게 드리프트됨
  • 계정 잠금 우려로 사용을 자제하게 됨
  • 마크다운 규칙으로도 성향 제어가 잘 안 됨
클로드가 기록하라는 지시를 누락하는 문제는 왜 생기나요?

클로드에게 기록해두라고 지시했는데도 계속 잊어버리고 나중에 지적하면 놓쳤다고 인정하는 패턴이 반복된다는 질문이 올라옴. 설정 문제인지 md 파일이 길어서 못 읽는 건지 문의함. 별도 답변은 대화에 나오지 않음.

  • 기록 지시를 반복적으로 잊는 문제 제기
  • md 문서 길이가 원인인지 의문 제기
  • 세팅 방법 문의
논문 자동분석은 어떻게 활용하면 좋을까요?

Claude에 논문 자동분석을 걸어두면 필요할 때 찾아볼 수 있어 편하다는 활용 경험이 공유됐다. 다만 아카이빙해 두면 오히려 잘 안 보게 되는 경향도 함께 언급됐다. 그래도 필요 시 검색해 참고한다는 의견이었다.

  • Claude로 논문을 자동 분석·축적하는 활용 사례가 나왔다.
  • 필요할 때 검색해 찾아보는 방식이 편리하다고 평가됐다.
  • 축적한 자료를 평소에는 잘 안 보게 된다는 반응도 있었다.
